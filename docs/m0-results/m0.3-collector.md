Contracts:

## Task 3.2: `collector/state.py` (RunState, RunRegistry)
Files: `coroner/collector/state.py`, `tests/unit/collector/test_state.py`. No `coroner/evidence/*` file changed.
### Interfaces
- `RunState` (dataclass, `eq=False`): `run_id`, `highest_seq` (None until a Sample), `seen: IntervalSet`, `last_sample_recv_time`, `last_sample_monotonic`, `interval_ms`, `next_gap_number` (starts at 1), `silence_open`, `terminated`, `dirty`, `loaded`, `lock: threading.Lock`; `mark_dirty()`, `apply(Outcome)`. Field names are the design's (design lines 345 to 353); `loaded` is the only addition.
- `Outcome(new_sample: NewSample | None, gap_ids: tuple[str, ...], silence_opened: bool, terminated: bool)` and `NewSample(seq, recv_time, interval_ms, monotonic)`. `apply` takes an already-classified outcome after a durable write, checks every input before changing anything, requires the run lock and a loaded, clean run (else `RunDirtyError`). A new Sample clears `silence_open`; gap ids raise `next_gap_number` to 1 + the highest id; it never goes down.
- `RunRegistry(config, *, fsync=os.fsync, fsync_dir=fsync_directory, now=None, replay_hook=None, volume_lock=None)`: `start() -> StartupReport`, `close()` (idempotent, also a context manager), `get(run_id)`, `lock(run_id)` (context manager), `open_run(run_id)` (caller holds the run lock, as in the design pseudocode), `append(state, records)` (the gate: refuses a dirty or unloaded run, marks the run dirty on `OSError` or `TailRepairRequired`), `ensure_rejections_ready()`, `mark_rejections_dirty()`, `writer`, `rejections_dirty`. The registry guard protects only the dict and is never held during file I/O.
- `VolumeLock(directory, *, flock=None)`, `CollectorAlreadyRunning`, `CollectorStartupError`, `RunDirtyError`, `scan_records(records) -> RunSnapshot`, `gap_id_number`, `COLLECTOR_VERSION`.
- `COLLECTOR_VERSION = "0.1.0"`: the design's `run_metadata` example value. No version constant existed and `pyproject.toml` says `0.0.0`; this constant is the single source until a release decision changes it.
### Startup sequence (`RunRegistry.start`)
1. Create the evidence directory if missing. Fail if the path exists and is not a directory.
2. Verify writability with a real write to an auto-deleted temporary file (`tempfile.TemporaryFile`, leaves nothing behind).
3. Take `.collector.lock` (POSIX `flock`, exclusive, non-blocking).
4. For each `*.jsonl` in sorted order: run `repair_file`, then under Crash_Durable fsync the file explicitly (a complete last line does not prove an earlier fsync succeeded). `_rejections.jsonl` is included (null run_id repair record). Names that are not evidence files (`_other.jsonl`, names with spaces, directories named `*.jsonl`) are skipped and listed in `StartupReport.skipped`, never repaired or changed. `.collector.lock`, `.coroner_probe/` and other non-`*.jsonl` entries are ignored.
5. Under Crash_Durable fsync the evidence directory (after every restart). On win32 `fsync_directory` is a no-op, as in the writer. The directory's own entry in its parent is not synced (the evidence directory is a volume mount point).
6. Under Process_Durable no fsync is issued (flush to the operating system only; the design level).
A directory-level failure (create, not writable, lock, directory fsync) raises `CollectorStartupError` and releases the lock. A per-file repair or fsync `OSError` does not stop startup: that run is created dirty (or `rejections_dirty` is set) and is gated until `open_run` (or `ensure_rejections_ready`) succeeds.
### Recovery sequence (`open_run`, first open or dirty run)
tail repair (`repair_file`) -> fsync file and directory (Crash_Durable; skipped only if this process already verified the file and the run is not dirty) -> replay hook (**owned by Task 3.5, default is a documented no-op; no gap regeneration is implemented here**) -> rebuild state from `read_evidence` -> on first open in this process write `run_metadata` (`resumed` if the file has any valid record, else `created`) -> clear `dirty` and set `loaded`. Any exception leaves the run dirty and re-raises. A dirty run already loaded repeats recovery without another metadata record. State changes only after the metadata write succeeded.
### State reconstruction rules
- Only valid, non-quarantined records count. Only `sample` records feed `highest_seq`, `seen`, `interval_ms` (last Sample) and `last_sample_recv_time` (last Sample). `sequence_anomaly` never counts. A Sample line isolated by repair (D19/D30) is not a record and never counts.
- `next_gap_number` = 1 + highest number among valid gap records whose `gap_id` is `gap-` plus ASCII digits only (full match; `gap-٣`, `GAP-9`, `gap-1\n`, `gap-` are ignored).
- `terminated` iff a valid `termination` record exists. `silence_open` iff a `silence_timeout` gap exists with no valid `sample` record after it in file order. Historical silence gaps are never re-emitted.
- Records in the file count as persisted even if they were never acknowledged (design "ack-lost"): a Probe retry is then classified as a duplicate.
- `last_sample_monotonic` is None after loading; it is never derived from wall-clock time. Watchdog (Task 3.9) rule: skip any run whose `last_sample_monotonic` is None (this is the design's "only runs that received a Sample during this process lifetime"). An in-process rebuild keeps the existing value.
### Durability operations and dirty handling
- `run_metadata.durability` and `fsync_before_ack` come from the writer's configured level (`crash` <-> `true`, `process` <-> `false`). `evidence_file` is `<run_id>.jsonl` (D31).
- New file under crash: write, flush, fsync file, fsync directory (observed in tests as `[fsync_file(size), fsync_dir]`). Startup of a clean file: `[fsync_file(size), fsync_dir]`. Startup of a damaged tail: repair's own file fsync, explicit file fsync, directory fsync, all at the final size.
- A failed write, partial write, flush or fsync (injected) during the metadata write or an append leaves `dirty` set, the in-memory state unchanged, further appends and `apply` refused (`RunDirtyError`), and the retry through `open_run` repairs, re-syncs and succeeds.
### Lock behaviour
- POSIX: `os.open(.collector.lock, O_RDWR|O_CREAT, 0o600)` then non-blocking exclusive `flock`. Contention raises `CollectorAlreadyRunning` ("another Collector already holds ...") and closes the descriptor; any other error raises `CollectorStartupError`. `release` closes the descriptor (dropping the lock), is idempotent, and never deletes the lock file or any evidence.
- win32: `acquire` is a no-op (design: documented no-op), creates no file, `held` stays False.
- Real `flock` tests are skipped on win32; the contention and error mapping run on win32 through the injectable `flock`.

## Task 3.2 correction: created vs resumed

**Rule.** `RunRegistry.open_run` decides the `run_metadata` `event` from file existence, checked once before the file is opened, created or repaired: `event = "resumed" if the file existed else "created"`. The old rule ("created if the file has no valid record") is removed. An existing file is therefore `resumed` even when it is empty (0 bytes) or holds only malformed evidence.

**Design quote** (design.md, Data Models, run_metadata): "The first record of a file when it is created, and again each time the Collector reopens an existing run file after a restart."

**Startup scan.** `RunRegistry.start` repairs existing files but never creates one, so it does not change existence before `open_run` looks.

**Retry on a new file.** If the first metadata write on a new file fails after the file was created (for example the file fsync raises), the run stays dirty and unloaded. The file now exists and may hold a partial or complete first record. The retry of `open_run` sees an existing file, repairs its tail and writes `resumed`. A file can therefore contain `created` followed by `resumed` with no restart between them. This follows the approved rule, and no evidence is dropped.

**Directory fsync.** The writer decides the directory fsync for a new file on its own existence check inside `append`, which still holds for `created`. For an existing file under Crash_Durable, `open_run` already fsyncs the file and the directory. Neither path changed.

**Tests** (`tests/unit/collector/test_state.py`): the old test `test_file_with_nothing_valid_is_treated_as_created` was replaced. New file gives `created` (existing tests). Parametrized `test_existing_file_is_resumed_and_original_bytes_survive` covers empty, malformed-only, unterminated fragment, fragment plus NUL, fragment plus NUL plus partial repair record, and a valid file. It checks `resumed`, that the original bytes remain a prefix (sha256 compared), and that the record passes `validate_record`. `test_existing_file_is_resumed_even_when_startup_scan_was_skipped` covers an empty file that appears after startup. `test_retry_after_failed_metadata_write_on_new_file_is_resumed` covers the retry case.

## Task 3.3: `collector/storage_probe.py`

### Interface

`StorageProbe(evidence_dir, *, fsync=os.fsync, fsync_dir=coroner.evidence.writer.fsync_directory, clock=time.monotonic, opener=io.open-like (path, mode), mkdir=os.mkdir)`.

* `check(force=False) -> ProbeResult`: cached result when fresh, otherwise a real probe. Never raises.
* `run_startup()`: `check(force=True)`, the forced probe before readiness.
* `invalidate()`: drops the cache now; the caller (ingest path, Task 3.11) calls it after a failed append. No HTTP wiring here.
* `ProbeResult(ok, step, error, checked_at)`. `error` is a one-line reason of at most 200 characters and is what the health body's `storage_error` will carry (Task 3.11). `step` and `checked_at` are extra to the design's health fields and need not be exposed.

### Probe sequence

`mkdir` `.coroner_probe` if missing (evidence dir must already exist) -> `open probe.tmp "wb"` -> `write` one unique token line (uuid4 plus counter) -> short write fails -> `flush` -> `fsync(file)` -> `close` -> `fsync_dir` for each directory newly created (`.coroner_probe` when `probe.tmp` was created, evidence dir when `.coroner_probe` was created; deepest first; a failed directory sync stays pending and is retried) -> fresh `open "rb"`, `read` the whole file -> exact byte equality with the token. The probe file is overwritten by each probe (design: "truncate or replace") and never deleted. Symlinks at either reserved path fail the probe.

### Durability semantics found in the design

Design lines 281 (steps), D21 ("real write+fsync+read-back probe") and Property 28 list `fsync` and directory fsync as unconditional steps, and the task text agrees, so the probe always fsyncs whatever Durability_Level the run uses. One sentence (design line 283, "checks writability and persistence at the configured level") could be read as "skip fsync under Process_Durable"; nothing else in the design supports that reading, and the stricter reading can only turn `storage_ok` false, never true, so it was not adopted. Flagged for the orchestrator. On win32 the default `fsync_dir` is the writer's no-op; no separate bypass exists.

### Failure injection (recorded events, from tests)

First probe, success: `mkdir, open:wb, write, flush, fsync, close, fsync_dir:.coroner_probe, fsync_dir:evidence, open:rb, read, close`. Existing dir and file: `open:wb, write, flush, fsync, close, open:rb, read, close`.

| Failure | step | Events recorded |
|---|---|---|
| mkdir | mkdir | `mkdir` |
| open | open | `mkdir, open:wb` |

| mismatch, prefix-only, extra byte | compare | full sequence |

### Cache and invalidation

Fresh iff `0 <= now - checked_at < 1.0` (at exactly 1.0 s it is stale; a backwards clock is stale). `checked_at` is taken at probe start. Failed results are cached too. `invalidate()` bumps a generation counter and clears the cache; a probe that started before the bump returns to its own caller but is not cached, so it is never served as fresh later (tested).

### Isolation and concurrency

With run files, `_rejections.jsonl` and `.collector.lock` present, sha256 and mtime are unchanged after three forced probes; every write-mode open is `.coroner_probe/probe.tmp`; the evidence dir holds only those names plus `.coroner_probe`. One probe lock serialises real probes (not a run lock); a waiting caller re-checks the cache and shares a cached result or probes itself. A separate small state lock guards cache and generation and is never held during I/O. Test: 8 threads x 10 calls, 80 results all ok, never two probes in flight.

## D32 note (StorageProbe strictness)
Design decision D32 (decision table, after D31) records that `StorageProbe` always requires a successful write, flush, file fsync, applicable directory fsync, read-back and exact comparison, under both `process` and `crash`. It resolves the design sentence "The probe checks writability and persistence at the configured level" in favour of always fsyncing (that sentence now says "at every durability level (see D32)"). `storage_ok=false` does not necessarily mean a Process_Durable append would fail. A successful fsync does not prove physical-media persistence (Requirement 15.9 wording). Ordinary append semantics are unchanged. No schema change.

## Task 3.4: Property 28, Collector half
File: `tests/unit/collector/test_prop_storage_ok.py` (296 tests).
### Contract tested
`storage_ok` is taken as `ProbeResult.ok`. (1) all steps succeed => ok; (2) any required step fails => not ok; (3) `step` is the first failing step in the fixed order; (4) `error` is a non-empty, at most 200 character, single-line, printable string that starts with the step name; (5) no run file, `_rejections.jsonl` or `.collector.lock` changes (sha256, size, mtime) and every write-mode open is `.coroner_probe/probe.tmp`; (6) `invalidate()` drops a cached success; (7) the next check after invalidation verifies storage again (events recorded); (8) a probe in flight during `invalidate()` does not repopulate the cache.
### Strategies and oracle
Per-step outcome flags: mkdir, open (write), write (ok, raise, short), flush, file fsync, close (write handle), directory fsync for `.coroner_probe` and for the evidence directory (each applicable only when that entry was newly created or is still pending), open (read), read, close (read handle), compare (ok, mismatch, prefix, extra byte). Also: probe directory and file already existing or not (3 initial states), durability `process` or `crash` (via `load_config`; the probe has no durability input), and operation sequences of 1 to 9 steps (`check`, forced check, `run_startup`, `invalidate`, clock advance of 0, 0.5, 0.75, 0.9375, 1.0, 1.25, 2.0 or -0.5 s). Flag generators mix a sparse variant (about 1 in 7 fails) and a dense one (1 in 2).
The oracle (`oracle_probe`, `Model`) is written in the test with its own step-order table and its own model of the probe directory, file and pending directory fsyncs. It does not call `check()` and imports nothing private. It also models the cache (fresh iff `0 <= now - checked_at < 1.0`). Cleanup modelled explicitly: after a failed write, short write, flush or fsync the write handle is still closed (event `close`) and a close failure there is masked; a close failure with no earlier failure is fatal (`close`, no directory fsync follows); a failed `open:wb` leaves no handle; the read handle is closed after a failed read, and a read-handle close failure reports `read`; a directory whose fsync failed stays pending and is synced on the next probe, probe directory first.

### Explicit cases

### Cache, invalidation, concurrency
Success reused at 0.999 s and re-probed at exactly 1.0 s; a cached failure is reused within 1 s even after storage recovers, and recovery happens after expiry; invalidation at the same instant forces a real probe; repeated forced probes and `run_startup` always verify. Interleavings are deterministic: a hook blocks the first `fsync` of the probe in flight on a `threading.Event` (10 s upper bound only), `invalidate()` is called while it is blocked, then it is released. The invalidated result (success or failure) is returned to its own caller and not cached; without invalidation it is cached; a waiting caller shares the cached result (1 probe) or runs its own probe after an invalidation (2 probes). Eight threads x 10 calls (half forced): 80 ok results and the event log is exactly one fresh sequence followed by whole existing-state sequences (no interleaving).
### Isolation
Every Hypothesis example creates run, rejections and lock files and compares sha256, size and mtime afterwards, asserts every write-mode open is `.coroner_probe/probe.tmp`, and that only `.coroner_probe` was added. A separate test does the same with the real default operations (`os.fsync`, three forced probes, both durability levels).
### Negative controls
The harness rejects a probe that swallows directory fsync failures, a constant `ok=True` probe, and a run where failure injection is disabled; with nothing failing and injection off it agrees.
### Defects found and fixed in Task 3.3 code (`coroner/collector/storage_probe.py`)
1. A close failure after an earlier failed write, flush or fsync replaced the earlier step: the "do not mask" guard used `sys.exc_info()` inside the `except` handler for the close error, where it is the close error itself, so the guard was always false. Counterexample: `fsync` and `close` both failing reported `close` instead of `fsync`. Fix: an explicit `step_failed` flag, and the unused `_in_flight_step_error` helper was removed.
2. `error` could contain non-printable characters (for example a NUL or ESC from an exception message). Counterexample: message `"\x00\x1b[31mred\x07"`. Fix: `_short` replaces non-printable characters with `?` after collapsing whitespace.
No other production file changed.

## Task 3.5: `collector/service.py` (IngestService)

### Interface
`create_ingest_service(config, *, fsync, fsync_dir, now, monotonic, storage_probe, volume_lock) -> IngestService` builds a `RunRegistry` with a `GapReplay` as its `replay_hook`, attaches it, and returns the service (the caller runs `registry.start()`). `IngestService(registry, *, storage_probe, now, monotonic)` raises `ValueError` if the registry's hook is not a `GapReplay`, so recovery cannot be skipped by accident.
- `ingest(raw_body: bytes) -> IngestResult(http_status, body, kind, run_id, seq, durability, recv_time, gap_ids, rejection_recorded, ingest_ms)`. `kind` is `stored`, `duplicate`, `reset` (200), `rejected` (413, 422), `storage_failure` (503) or `internal_error` (500). It never raises for bad input or storage failure.
- `record_termination(run_id, raw_body: bytes) -> TerminationResult(http_status, body, recorded, run_id, rejection_recorded, ingest_ms)`.
- `replay_reports: Mapping[run_id, ReplayReport(run_id, replayed_samples, regenerated_gap_ids, conflicts, skipped_samples)]`; a conflict is `ReplayConflict(gap_type, detected_at_seq, expected, stored)`.
- Public pure helper `build_records(run_id, sample, recv_time, events, previous_recv_time, next_gap_number) -> (records, gap_ids)`.
- Bodies: 200 `{"status":"stored"|"duplicate"|"reset","run_id","seq","durability","recv_time"}` (the design says `stored`, not `ok`); 422 `{"error":"validation_failed","reason_code","field","reason"}` plus `"rejection_recorded": false` only when the rejection write failed; 413 `{"error":"body_too_large","reason_code":"body_too_large","field":"","reason"}` (the design gives no 413 body, this is the same shape); 503 `{"error":"storage_failure"}`; 500 `{"error":"internal_error"}`; termination 200 `{"status":"recorded"}`.
- Naming: the design and the task text say `SequenceTracker`; the implemented API is `evidence.gaps.SeqState` and `classify`, which the service uses.

### Ordering
Size check, strict JSON parse, `validate_sample`, per-run lock, `open_run`, `classify`, `build_records`, `validate_record` on every generated record, one `registry.append`, `RunState.apply`, acknowledge. The acknowledged `durability` is `AppendResult.durability` (what the writer did). A test spies on `registry.append` and checks that the state is unchanged before and during it.

### Sequence and gap generation
Classification, drop-range derivation and reconciliation come from `evidence.gaps` (`classify`, `derive_drop_range` through `SeqEvents.drop`, `reconcile`). First `seq > 0` gives a discontinuity `[0, seq-1]`; duplicate and reset become one `sequence_anomaly` record with the Sample as received and no gap; the baseline is not moved. Batch order is Sample (or anomaly), discontinuity gap, drop gap, ids `gap-NNNN` from `next_gap_number`. Two gaps of one ingest are reconciled against each other before the write (identical range `reconciled`, partial `partial_overlap`, unknown range `none`).
Times, since the design gives only examples: live `end_time` and gap `recv_time` are the detecting Sample's receive time; `start_time` is the previous accepted Sample's receive time (the design examples), or the detecting Sample's receive time when none exists. Replay uses the same `start_time` and `end_time`, read from the persisted Sample records. A regenerated gap's `recv_time` is the time recovery ran (the envelope says "receipt, detection, or repair"); it is not back-dated.

### Record validation (D31)
Every generated record (sample, anomaly, gaps, rejection, termination, regenerated gaps) goes through `validate_record` before the write; a failure writes nothing and returns 500 `internal_error`. Rejection `reason_code` is the first `validate_sample` issue's code (all within the D31 set); `http_status` is 413 or 422, `body_len` is the raw length, `body_preview_b64` is the base64 of at most the first 1024 bytes. Strict JSON: `NaN`, `Infinity`, `-Infinity`, invalid UTF-8 and parser recursion errors are `invalid_json`. Duplicate object keys are not detected (the design does not ask for it).

### Replay (`GapReplay`, D26 item 4)
Runs inside `open_run` after tail repair and before the state rebuild. It replays the valid `sample` records in file order through `classify` and `SeqState.apply`, derives the expected discontinuity and drop gaps, and compares them with stored gaps by semantic identity (never `gap_id` or times). Missing gaps are appended in one durable append with ids from `max(scan_records(...).next_gap_number, state.next_gap_number)`. Reconciliation of a regenerated gap uses the same-ingest peers (same `detected_at_seq`, other gap type), stored ones included, plus other regenerated gaps of that Sample (D29). A stored gap with the same type and `detected_at_seq` but other fields is a conflict: logged at WARNING, returned in `ReplayReport.conflicts`, nothing added and nothing overwritten. Silence gaps, anomalies, malformed and isolated lines are never used. Late Samples stay `reset` because they were never stored as Samples. A second replay adds nothing (tests and a Hypothesis property). An append failure inside replay leaves the run dirty through `open_run` and surfaces as 503. A stored peer that was written without the reciprocal `reconciles_with` entry is not edited (no overwrite); the reader recomputes from ranges.
Ack-lost retry: a persisted Sample whose acknowledgement was lost is a `duplicate` on retry, before and after a restart; a partial batch (Sample complete, gap line cut) is repaired and the gap regenerated once as `gap-0001`.

### Rejections
Valid run id: through `open_run` under the run lock, into the run file (this creates the run file when the run is new, as the design's "written to the run file when the Run_Identifier is valid" implies). Missing or invalid run id, unparseable JSON, oversized body: `_rejections.jsonl` with null `run_id`, serialized by a service lock because that file has no run lock. A failed persistence keeps the status, adds `rejection_recorded: false`, invalidates the probe and logs; `_rejections` is marked dirty and repaired before its next append.

### Failure handling
`OSError` or `TailRepairRequired` from `open_run` or the append gives 503 `storage_failure`, no acknowledgement, the run dirty (set by the registry), in-memory state unchanged and `storage_probe.invalidate()`. The next ingest runs recovery (repair, replay, reload). Tests cover write, partial write, flush and fsync failures, a failed `run_metadata` write, a failed rejection write (run file and `_rejections`) and a failed termination write.

### Termination
`record_termination(run_id, raw_body)`: the body is a JSON object with `source`, `observed_time`, `container_state{status, exit_code, oom_killed}`, `cause_label`, `note`; the design lists no request schema, so this is the record's own payload, with the envelope added by the Collector (envelope keys in the body are `unknown_field`). `validate_record` is the only validation and no cause is inferred. Invalid run id: 422 to `_rejections`; invalid body: 422 and a rejection in the run file; oversized body: 413 (the design table lists only 422 for the route, 413 is used because the code `body_too_large` exists). `RunState.terminated` is set through `apply(Outcome(terminated=True))` only after the append returned. Samples after a termination are still accepted (design Experiment B: late pre-kill Samples are valid). A second termination is recorded as another record (the design is silent). The termination path invalidates the probe on a persistence failure like ingest does. The silence watchdog (Task 3.9) must skip runs with `terminated` set.

### Observability
Logger `coroner.collector.service`, one INFO line per ingest and termination: `ingest run_id=... seq=... kind=... http=... ingest_ms=...`, with `ingest_ms`, `http_status` and `ingest_kind` as `LogRecord` attributes. Raw bodies are never logged. `monotonic` is injectable and is also the clock stored in `NewSample.monotonic`, so the watchdog must use the same clock.

## Task 3.7 correction: recv_time under the lock

### Problem

`test_two_threads_ingest_into_one_run` (in `tests/unit/collector/test_prop_isolation.py`) failed intermittently, about 2 of 7 runs. The service read `recv_time` before taking the run lock. Two concurrent requests could therefore read their times in one order and write in the other, leaving a run file whose records were not in `recv_time` order.

### Approved fix

`coroner/collector/service.py` now reads `recv_time` (`self._now()`) only after the lock that serialises the target file is held, and after `open_run` for a run file. File order is then receive order. No record field, routing, status code or response body changed. `IngestResult.recv_time` still equals the stored value. `ingest_ms` is still measured from request start with the monotonic clock, so it includes any wait for the lock.

| Path | Where `recv_time` is read |
| --- | --- |
| valid Sample ingest | `_ingest`, inside `registry.lock(run_id)`, after `open_run` |
| run-file rejection (valid `run_id`) | `_persist_rejection`, inside `registry.lock(run_id)`, after `open_run` |
| `_rejections.jsonl` rejection, including 413 and `invalid_json` | `_persist_rejection`, inside `self._rejections_lock` |
| termination | `_terminate`, inside the run lock, after `open_run` |
| replay-regenerated gaps | `GapReplay.__call__`, called from `open_run` under the run lock; stamped with the recovery time, which precedes the request's own `recv_time` |

## Task 3.7 correction 2: recv_time is Receive_Time (captured at request start)

**Design.** `design.md`, "Collector persistence", pseudocode `IngestService.ingest(raw_body)` (lines 312-314): the first statement is `recv = utc_now_ms()`, before `if len(raw_body) > max_body: -> reject(413)`, before `parse_json`, before `validate_sample`, and before `with registry.lock(run_id):`. The same section's `build_records(obj, recv, events, ...)` then uses that value. The stored-record section defines `recv_time` as the Receive_Time (Collector clock, when the Sample was received). The design already states this, so no decision-register entry was added.

**Why the earlier fix changed semantics.** The first Task 3.7 correction moved the clock read under the run lock (and the `_rejections` lock) to make `recv_time` non-decreasing in file order. That turned `recv_time` into a lock-acquisition time and made it wait-dependent, which departs from the design's Receive_Time.

**Change (`coroner/collector/service.py`).**
- `ingest()` and `record_termination()` read `self._now()` once, first thing, before the size check, validation and any lock. The value is passed through `_ingest`/`_terminate`, `_rejected`/`_termination_rejected` and into the record built for the Sample, anomaly, gaps, termination or rejection. It is never replaced by lock-acquisition or append time. The response `recv_time` is that same value.
- `_persist_rejection` now receives the finished record instead of a builder callback; it no longer reads the clock. Run-file rejections, `_rejections.jsonl` rejections, 413, `invalid_json` and duplicate-key rejections all carry the request-start time.
- Termination validation uses the real `recv` instead of a placeholder; `_PLACEHOLDER_TIME` was removed (unused).
- `ingest_ms` is still measured from the start of processing with the monotonic clock. Per-run locking, sequence state, routing, status codes, bodies and record fields are unchanged.
- Replay-regenerated gaps keep the recovery-time `recv_time` (approved, unchanged). `recv_time` need not increase in file order.

**Oracle fix.**
- `tests/unit/collector/test_prop_isolation.py`: `Clock` records the first reading of each tracked request (its arrival) per thread; `Env.ingest_tracked` returns the result and stores `(run, seq, arrival, result)`. `check_files(..., ordered=...)` keeps the `recv_time` sort check for the single-thread scenarios (valid there) and `verify_serialized` passes `ordered=False`. No sorting is applied to concurrent files.
- `tests/unit/collector/test_service.py`: `test_file_order_is_receive_order_when_the_first_reader_of_the_clock_is_held_back` asserted the reverted behaviour and was replaced by `test_recv_time_is_the_arrival_time_even_when_the_earlier_request_persists_later` (same six parametrized cases: sample-sample, run rejection then sample, termination/sample both ways, and two `_rejections.jsonl` cases).

## Task 3.8: Property 7, persistence precedes acknowledgement

**File.** `tests/unit/collector/test_prop_ack_after_persist.py` (46 tests). It runs the real `IngestService`, `RunRegistry` and `EvidenceWriter` on real files. A recording double replaces `open` in `writer` and `state` and the injected `fsync` and `fsync_dir`, and logs open (`O`), write with bytes (`W`), flush (`F`), file fsync with the file size (`S`), directory fsync (`D`), the injected failure (`X`) and the acknowledgement (`A`).

**Independent oracle (hand-written table, no production append logic).**

| level | file | tokens of one clean write group |
|---|---|---|
| process | any | `O W F` (no fsync, ever) |
| crash | existing | `O W F S` |
| crash | new, or an earlier creation whose directory sync did not finish | `O W F S D` |
| crash | recovery sync (dirty run) | `O F S D` |

A request must consist of, in order: repair `R` (iff the file tail is unterminated or not a JSON object), recovery sync `Sy` (iff crash level and the run is dirty), at most one regenerated-gap append `G`, `run_metadata` `M` (iff none completed in this process), then the batch `B`. A 200 needs every group complete and matching the table, and the fsync size equal to the size before the batch plus the batch length. A 503 needs the injected failure in the last group, no state change (state equals the rebuild from the bytes before the failed batch, or the pre-request state if recovery itself failed), the run dirty, exactly one probe invalidation and the earlier bytes unchanged as a prefix.

**Property test.** `test_property_7_...` draws 1 to 4 ingests (skips of 0, 1 or 3, drops of 0 to 2, repeats), either level, a new or an existing file, and either no failure or one of write, partial write (cut after 0, 1, half, last byte or all bytes), flush, file fsync, directory fsync, at event 0 to 4, firing once or twice (the second firing hits the recovery of the first). Each failed ingest is retried until it succeeds. Settings: `max_examples=200`, `derandomize=True`, `database=None`, `deadline=None`. Statistics run (`--hypothesis-show-statistics`): 200 passing, 0 failing, 49 invalid (generation overruns, not test rejections); failures fired in about 28% of examples.

**Other tests.** Exact event order for first ingest (crash new `OWFSD OWFS A`, crash existing `OWFS OWFS A`, process `OWF OWF A`), a batch of 1 versus 3 records in one write, failures at the first and last byte of a 3-record batch, a failed directory fsync at creation (retry still syncs the directory), the table's rejection of misordered or incomplete groups, eight negative controls run as monkeypatched mutants (ack after a failed append, state applied before the append, `mark_dirty` skipped, probe invalidation skipped, `crash` reported without fsync, file fsync skipped, directory fsync skipped, recovery sync skipped) which the oracle catches, and these mutation scenarios passing on the real code.
