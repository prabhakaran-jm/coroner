## Timing boundaries (offset-corrected Capture_Time vs kill)
| Capture | Category |
|---|---|
| kill - 1 us | `pre_kill` |
| kill | `within_tolerance` (not pre_kill) |
| kill + 250 ms | `within_tolerance` (inclusive) |
| kill + 250 ms + 1 us | `post_kill_beyond_tolerance` (fails B) |
| kill + 251 ms | `post_kill_beyond_tolerance` (fails B) |

Categories are exclusive. `pre_kill_late_received` (recv_time > kill) is a flag on `pre_kill`; Receive_Time never changes the primary category. `after_container_stop` (capture > FinishedAt) is independent and does not fail a run by itself; it fails only when the Sample is also beyond tolerance. B passes iff at least one pre-kill Sample, none beyond tolerance, and the other five checks pass.

## Contract notes
1. `stopped_within_10s` and `no_shutdown_handler_records` are keyword-only inputs, not derived inside `evaluate_experiment_b`. Design pseudocode treats both as free inputs (the first needs the runner clock, the second the evidence scan), so this is consistent. The experiment-B flow (6.15) must compute and pass them; each must be exactly `True`.
2. `evaluate.ContainerState` (exit_code, oom_killed, status) and `manifest.ContainerState` are different classes. Evaluators read `exit_code` and `oom_killed` by attribute, so either works for B and C. `evaluate_container_state` (A/B/C Property 21) requires the `evaluate` class. This is documented in the `evaluate.py` module docstring.
3. The manifest does not yet write `diagnostics`, `sampling_limitations` or `sample_timing` blocks. `BTiming.to_dict()`, `DiagnosticMetrics.to_dict()` and `SamplingLimitations.to_dict()` exist, but no test yet checks they land in the manifest. Add that test at 6.15/6.16.
4. The design's example JSON shows statement 1 as "up to about 2 MiB can grow between two Samples", while the design pseudocode and the implementation say "of growth can occur between two Samples". Cosmetic; no code change.
