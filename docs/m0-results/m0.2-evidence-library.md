## Current M0.2 contracts — supersedes earlier checkpoint notes

The sections below are a chronological log and are kept unchanged, including test runs, decisions and observations that later work superseded. Where an earlier section disagrees with this list, this list is authoritative (state at the M0.2 checkpoint, Task 2.18, 15 November 2026). The decision IDs refer to the register in `.kiro/specs/coroner-m0/design.md`.

1. **All seven record types are fully payload-validated.** `validate_record` checks the envelope and the full payload of `sample`, `run_metadata`, `gap`, `sequence_anomaly`, `rejection`, `repair` and `termination` (Task 2.19, clarified by D31). Statements in earlier sections that the six non-sample payloads are "envelope-validated only" or "unvalidated" are superseded. `read_evidence` quarantines a record with an invalid payload as `invalid_record`, so it never reaches `summarize`.
2. **`last_sample_time` uses `recv_time`.** It is the envelope `recv_time` (Receive_Time) of the last valid `sample` record in file order, not the maximum `recv_time` and not `sample.ts` (Task 2.17, design Property 13). Statements in earlier sections that it is the Sample `ts` are superseded.
3. **`TAIL_LINE_CAP` = 2 MiB (2,097,152 bytes); `FRAGMENT_CAP` = 1 MiB (1,048,576 bytes)** (D28). A last line longer than 2 MiB is not parsed and is invalid; a repair record copies at most the first 1 MiB of the fragment, with `fragment_len` the true length and `fragment_truncated` true exactly when it exceeds 1 MiB. Earlier mentions of a 1 MiB inspection limit or a 768 KiB limit are superseded.
4. **D30 invalidating marker.** For an unterminated last line, repair appends one NUL byte, the isolating newline and the repair record in one durable append. The original file bytes remain an unchanged prefix, but the isolated physical line is the original fragment plus the marker (one NUL per repair attempt whose marker persisted), so it is not byte-identical to the fragment; `fragment_len` and `fragment_b64` describe the fragment without that attempt's marker. Earlier statements that the isolated line is the fragment itself are superseded.
5. **Reconciliation warnings use the same-ingest scope** (D29). `summarize` compares a gap's stored `reconciliation` and `reconciles_with` only with gaps that share its `detected_at_seq`; overlaps with gaps from other ingests are not disagreements. `missing_sample_count` and `unreconciled_drops` still use all gaps in the file. Earlier statements that warnings compare every gap in the file are superseded.

## Task 2.1: `coroner.common` helpers (14 November 2026)

Files: `coroner/common/timeutil.py`, `coroner/common/envparse.py`, `tests/unit/common/__init__.py`, `tests/unit/common/test_timeutil.py`, `tests/unit/common/test_envparse.py`. `coroner/common/__init__.py` stays empty. Standard library only (checked by the structure tests, which still pass).

Contracts:
- `utc_now_ms(now=None) -> datetime`: aware UTC datetime truncated to milliseconds. `now` is an injectable clock for tests.
- `format_utc_ms(dt) -> str`: `YYYY-MM-DDTHH:mm:ss.sssZ`. Requires an aware datetime (naive raises ValueError), converts to UTC, truncates (never rounds) sub-millisecond digits, so formatting never carries into the next second.
- `parse_utc_ms(text) -> datetime`: strict inverse. Exactly three fractional digits and a literal `Z`; no offsets, whitespace, or non-ASCII digits; impossible calendar values (including a leap second and year 0) raise ValueError. The message names the value.
- `parse_int_env(name, raw, *, default, minimum=None, maximum=None) -> int`: `raw` is the variable's value (for example `os.environ.get(name)`), so the function is pure. None, empty, or all-whitespace gives `default`. Otherwise an optionally signed ASCII integer within inclusive bounds. Anything else raises `ConfigError` naming the setting and the value, for example `invalid CORONER_MAX_BODY='70000' (expected an integer from 100 to 60000)`.
- `parse_mem_size(text) -> int`: ASCII digits plus an optional unit `b`, `k`, `m`, `g` (any case), powers of 1024; a bare number is bytes (Docker reads it that way). No sign, decimal point, whitespace, or other suffix (`kb`, `mb`, `t` are rejected). The result must fit a signed 64-bit integer, which is Docker's limit. `0` is returned as 0; for Docker it means no limit, so callers that need a real limit must check for it. Errors raise `ConfigError` naming the value.
- `ConfigError(ValueError)` is defined in `envparse.py`.

## Task 2.2: `coroner.evidence.schema` (14 November 2026)

Files: `coroner/evidence/schema.py`, `tests/unit/evidence/__init__.py`, `tests/unit/evidence/test_schema_contract.py` (renamed to `test_schema.py` in task 2.3). Design file changed only by adding decision D25. Imports: standard library and `coroner.common.timeutil` (allowed by the dependency direction).

Implemented contract:
- `SCHEMA_VERSION = 1`; `RUN_ID_RE` is the approved `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$` (validation uses `fullmatch`, because `$` alone would accept a trailing newline); `RECORD_TYPES` is the seven design types in design order.
- `ValidationIssue(field, reason_code, reason)`, a frozen dataclass. `field` is a dotted path (`sample.seq`, `null_reasons.rss_bytes`) or `$` for the whole value.
- `validate_run_id(value) -> ValidationIssue | None`: string, 1 to 64 characters, matching the pattern. Every Run_Identifier problem (absent, wrong type, empty, too long, bad pattern, mismatch with the nested sample) has code `invalid_run_id`.
- `validate_sample(obj) -> list[ValidationIssue]`: returns every problem, in a stable order (required-field order, then `null_reasons` problems, then unknown fields); never raises; never modifies the input. Fields: `run_id`; `seq` integer at least 0; `ts` strict `YYYY-MM-DDTHH:mm:ss.sssZ`; `rss_bytes` and `request_count` integer at least 0 or null; `loop_delay_ms` number at least 0 and finite, or null; `pid` integer; `container_id` 64 or 12 lower-case hex, or null; `container_id_source` one of `mountinfo`, `cgroup`, `hostname`, `none`; `interval_ms` integer 100 to 60000; `dropped` integer 0 to 4,294,967,295; optional `null_reasons` object. A boolean is never an integer and a float is never an integer (a JSON `12.0` is rejected for `seq`). A nullable field that is absent is `missing_field`; a null needs a string reason of 1 to 200 characters in `null_reasons` (`null_without_reason` otherwise). Unknown fields are rejected (`unknown_field`).
- `validate_record(obj) -> list[ValidationIssue]`: for every record type, `record_type` in `RECORD_TYPES`, `schema_version` equal to 1 (an integer, not a boolean), `run_id` valid (null only for `rejection`), and `recv_time` a strict UTC millisecond timestamp. For `sample` records the nested `sample` must pass `validate_sample` (issues reported as `sample.<field>`), its `run_id` must equal the envelope's, and no other top-level field is allowed, so Capture_Time (`sample.ts`) and Receive_Time (`recv_time`) are both required and stay distinct. The payloads of the other six record types are validated by `validate_<type>` since Task 2.19 (see the Task 2.19 section at the end).
- Reason codes: `invalid_run_id`, `missing_field`, `wrong_type`, `out_of_range`, `invalid_format`, `null_without_reason`, `unknown_field`.

## Task 2.4: `coroner.evidence.writer` (14 November 2026)

Files: `coroner/evidence/writer.py`, `tests/unit/evidence/test_writer_contract.py` (named so task 2.5's `test_writer.py` and `test_prop_durability.py` are untouched; 2.5 may rename or extend it as 2.3 did). Imports: standard library, `coroner.common.envparse.ConfigError` (re-exported, not redefined; a test asserts the class lives in `coroner.common.envparse`), and `coroner.evidence.schema`.

Implemented:
- `Durability(str, Enum)` with `PROCESS = "process"` and `CRASH = "crash"`.
- `parse_durability(raw)`: unset or empty is `crash`; exactly `process` or `crash`; anything else (`Crash`, ` process`, `crash\n`, `0`, whitespace) raises `ConfigError("invalid CORONER_DURABILITY='x' (expected 'process' or 'crash')")`.
- `serialize_record(record) -> bytes`: `json.dumps(ensure_ascii=True, allow_nan=False, separators=(",", ":"))` plus one `\n`. Raises `RecordError` (a `ValueError`) for a non-mapping, NaN or infinity, a value JSON cannot hold, a circular reference, absurd nesting, an integer with too many digits, or any non-string key at any depth (json would silently turn `1` into `"1"`, breaking the round trip). ASCII output means valid UTF-8, and U+2028, U+2029, and newlines inside strings are escaped, so a record is always exactly one line.
- `fsync_directory(path)`: opens, fsyncs, and closes the directory (closing even if fsync fails); a documented no-op on Windows.
- `AppendResult(path, record_count, byte_count, created, fsynced_file, fsynced_directory)` with a `durability` property computed from the steps actually done: `crash` only if the file was fsynced and, for a newly created file, the directory too; an empty batch claims `process`.
- `EvidenceWriter(directory, durability, *, fsync=os.fsync, fsync_dir=fsync_directory)`:
  - `path_for(run_id)`: `<dir>/<run_id>.jsonl`; the reserved name `_rejections` maps to `_rejections.jsonl`; any other invalid id raises `ValueError` before any file access.
  - `append(run_id, records)`: checks every record first, then makes one write of all lines, a flush, and under Crash_Durable an `fsync` of the file and, if the file was created, of the directory. Returns an `AppendResult`.
  - `append_bytes_durably(path, data)`: raw append with the same steps and no validation, for repair records; the path must be inside the writer's directory (a sub-directory such as `.coroner_probe` is allowed); empty data is a no-op.
  - `close()`: marks the writer closed (idempotent). No file handle is kept between appends, so a file can be deleted or replaced afterwards, including on Windows.

Guarantees:
- **Validation before writing.** Every record in a batch must pass `validate_record` (envelope for all types, full nested Sample for `sample` records) and belong in the target file: in a run file `record["run_id"]` must equal the run id; in `_rejections.jsonl` only `rejection` records with `run_id` null are allowed. One bad record rejects the whole batch with `RecordError` (carrying the `ValidationIssue` list) and the file is byte-identical, with no fsync call. Since Task 2.19 the payloads of `run_metadata`, `gap`, `sequence_anomaly`, `rejection`, `repair`, and `termination` records are validated too (they used to be envelope-only); `test_non_sample_payloads_are_validated_since_task_2_19` replaces the test that documented the old gap.
- **Append-only.** Files are opened only in binary append mode. Existing bytes are never truncated, rewritten, or deleted, and the writer does not repair an incomplete last line (task 2.10 does; a test pins that the writer appends straight after any existing bytes).
- **Durability.** Process_Durable: write then flush, no fsync of any kind. Crash_Durable: write, flush, `fsync(file)` (with all bytes already on disk at that moment, checked through `fstat`), then, only for a file the call created, `fsync(directory)`. The order is tested with a recording double.
- **Failure boundary.** A failing write, flush, or fsync raises `OSError` and no `AppendResult` exists, so a caller cannot acknowledge. A failed flush never reaches fsync; a failed file fsync never reaches the directory fsync. After an `OSError` a partial line may remain, and a later append still works; the Collector must run tail repair first (design: `mark_dirty`).
- **Not thread-safe**; callers hold the per-run lock.

### Partial-write and repair contract

1. **A defect found and fixed (writer).** Under Crash_Durable the directory was fsynced only when the call that created the file succeeded. If that first call failed after creating the file (for example the file fsync failed or the write failed part-way), a retry saw an existing file, skipped the directory fsync, and returned a result claiming `crash` although the directory entry had never been synced. Fix: the writer remembers the files it created whose directory fsync has not yet succeeded and syncs the directory on the next successful append (and on `append_bytes_durably`); the entry is forgotten only after the directory fsync succeeds. Process_Durable never tracks or syncs a directory. Six tests cover the file-fsync, directory-fsync, partial-write, and `append_bytes_durably` retries and steady state; with the fix removed, 4 of them fail. Limit: the writer only knows about files it created itself; a file left by an earlier process is not synced again. The Collector's startup (task 3.2) should fsync the evidence directory once after its repair scan, so a first-run file from a crashed process is covered.
2. **Batch atomicity versus the design's wording.** The design says a Sample and its gap records "are therefore both durable together". The writer makes one write call, but if it fails part-way the file can hold some complete lines of the batch (a test shows lines 0 and 1 written, line 2 not). Repair sees a file ending in a valid line and does nothing, so a Sample line may exist without its gap record; the Collector returned 503 and the Probe never retries. Missing_Sample_Count is computed from gap records, so such a gap would be undercounted, and the in-memory run state (applied only after a durable write) would differ from the file until the next rebuild. Suggested handling for the Collector tasks (3.2, 3.5): after any `OSError`, mark the run dirty, run tail repair, and rebuild the run state by scanning the file before the next append, and have the reader treat a Sample whose predecessor sequence number is missing as a discontinuity even without a gap record. This is not in the approved design; it needs your decision. "Both durable together" should be read as "acknowledged implies both durable".
3. **Partial last line.** A partial line (cut anywhere, including exactly before the final newline) is what repair's `incomplete_last_line` and `missing_trailing_newline` branches isolate with an appended newline and a Repair_Record. This matches decision D19 (a valid-JSON line that lacked its newline is quarantined, because acknowledged records always end in a newline). The tests show the cases the writer produces. No mismatch.
4. **The writer does not enforce repair-before-append.** A test shows that appending after a partial line glues two records into one invalid line. The design relies on the Collector's `mark_dirty`. A writer-level guard (refuse `append` for a path after an `OSError` until repair clears it) would make this impossible to get wrong; it is not implemented and would need approval.
5. **A failed repair append** (`append_bytes_durably` of newline plus Repair_Record) can itself leave a partial line; re-running repair isolates that partial repair record as another Malformed_Line, and the original fragment stays in the file. Property 9 (idempotence) is about completed repairs; task 2.16 should state that scope.

Sequence and gap rules implemented (from the design table and decisions D6, D7, D8):
- First Sample at 0: `new`, no gap. First Sample above 0: `new` plus discontinuity `[0, seq - 1]`.
- `seq == highest + 1`: `new`, no gap. `seq > highest + 1`: `new` plus discontinuity `[highest + 1, seq - 1]`.
- `seq` already received as a Sample, or equal to the highest: `duplicate`. Below the highest and never received: `reset`.
- Anomalies keep `highest` and the received set unchanged, ignore `dropped`, and a reset number is not added to the received set (so the same reset sent twice is `reset` twice).
- A delayed Sample that fills an earlier discontinuity is a `reset`; the discontinuity stays recorded. A process restarted inside a run shows up as duplicates and resets, not as a new incarnation.
- A `dropped > 0` on a `new` Sample gives `range_status` `known` with the derived range, or `unknown` with the note `range starts below sequence number 0` or `range overlaps received samples`.
- Counting: `Missing_Sample_Count` is the union size of discontinuity ranges only (stored `missing_count` values are never read; drops, silence, and non-gap records are ignored). Unreconciled drops: an unknown or uncertain range contributes its `dropped_count`; a known range contributes the numbers no discontinuity covers; every entry is flagged `uncertain`.

Restart-related assumptions covered: the run state can be rebuilt by replaying only the received `sample` records through `classify` and `apply`. Because anomalies never move the baseline, the rebuilt state equals the live state and regenerates the same discontinuities; a first-seen number above 0 after a rebuild reports `[0, seq - 1]` missing (D6). ## Task 2.10: JSONL repair and recovery-before-append (`coroner/evidence/repair.py`)
Implemented (standard library plus `coroner.evidence.writer`, `coroner.evidence.schema`, `coroner.common`):
- `inspect_tail(path) -> TailInspection(ends_with_newline, last_line, last_line_valid_json, last_line_no, last_line_len)`. Read-only. Scans backward in 64 KiB chunks for the last newline. A last line is valid only if it is UTF-8 and parses as a JSON object; `NaN`/`Infinity`, arrays, bare scalars and lines over `FRAGMENT_CAP` (1 MiB) are not valid. An empty file has `last_line_no` 0. `last_line_len` is a field of this internal dataclass, not a record field.
- `repair_file(path, writer, now) -> record | None`. Returns None for a missing file, an empty file, or a clean tail (ends with a newline and the last line is a JSON object). Otherwise writes one `repair` record with exactly the design fields (`record_type`, `schema_version`, `run_id`, `recv_time`, `file`, `line_no`, `fragment_len`, `fragment_b64`, `fragment_truncated`, `reason`, `action`). `reason` is `incomplete_last_line`, `missing_trailing_newline` or `invalid_json_last_line`; `action` is `appended_newline` or `none_needed_already_terminated`. `run_id` is the file stem, or null for `_rejections.jsonl`. A file name that is not `<valid run_id>.jsonl` or `_rejections.jsonl` raises `ValueError` and the file is untouched. A malformed `now()` raises before anything is written.
- `writer.TailRepairRequired(RuntimeError)`, raised by `EvidenceWriter.append`.
Repair and isolation rules:
- Append-only. Nothing is truncated, moved or rewritten. The damaged bytes stay in the file as a Malformed_Line and are copied base64-encoded (up to 1 MiB; `fragment_len` is always the true length, `fragment_truncated` says whether the copy is partial) into the repair record.
- The isolating newline (when needed) and the repair record go out in ONE `append_bytes_durably` call at the writer's durability level. A write, flush or fsync failure propagates as `OSError` and no success is reported.
- Idempotent: a second call on a clean tail returns None and writes nothing. An interrupted repair leaves its own partial record as the new tail, which the next call isolates and records; no byte is ever lost (tested at every cut point of the repair append for three fragment kinds).
- Only the last line is examined. Gap records are not regenerated (task 3.5). Startup scanning and gating of runs (task 3.2) are not here.
Repair-before-append enforcement: `EvidenceWriter.append`, after validation and the empty-batch return, reads the file's last byte (`_tail_is_terminated`, via `io.open`, stateless). If the file is non-empty and does not end in `\n`, it raises `TailRepairRequired` and writes nothing. `append_bytes_durably` is not guarded, because repair itself uses it. A terminated but invalid last line does not block appends, since a new record cannot glue onto it; `repair_file` still records it. No batch atomicity is claimed: a failed batch can leave a partial line, and the next `append` is refused until `repair_file` runs.

## Correction: invalidating marker (D30)
Reopened correction to task 2.10 (found in task 2.16). Not task 2.17.

### Problem
A valid JSON Sample missing its final newline was repaired with `b"\n" + record` in one append. If the append stopped after the newline but before the record was complete, the Sample became newline-terminated valid JSON, the next repair named the partial record's line, and `read_evidence` counted a never-acknowledged Sample.

### Format change
For an UNTERMINATED last line only, `repair_file` appends ONE buffer through `writer.append_bytes_durably`: `b"\x00"` (`repair.INVALIDATING_MARKER`), `b"\n"`, then `serialize_record(record)`. The record fields and values are unchanged: `action` stays `appended_newline`, `fragment_len` is the true length of the line found (without this attempt's marker), and `fragment_b64` is the first 1 MiB of that line. A newline-terminated invalid last line is unchanged (`none_needed_already_terminated`, no marker, no newline). Schema version, FRAGMENT_CAP (1 MiB), TAIL_LINE_CAP (2 MiB) and durability semantics are unchanged. The physical isolated line is now the fragment plus one NUL, so it is not byte-identical to the fragment; the reader reports that physical length. The marker sits on the fragment's line, so the worst-case repair record line is unchanged (about 1.4 MB, below 2 MiB). The buffer is one byte longer.

### Interruption points (fragment F of length n, first record R of length r including its newline, buffer length r + 2)
| Cut (bytes of buffer persisted) | File state after the cut | Reader after the cut | Retries to converge | Reader after convergence (line of F) |
|---|---|---|---|---|
| 0 | unchanged | F `incomplete_last_line` | 1 (the full repair) | `isolated_by_repair`, n + 1 bytes, linked |
| 1 (marker) | `F\0` unterminated | `incomplete_last_line` | 1: records `F\0` (len n + 1, `incomplete_last_line`), appends `\0\n` + record | `isolated_by_repair`, n + 2 bytes (`F\0\0`), linked |
| 2 (marker + newline) | `F\0` terminated | `invalid_json` / `invalid_utf8`, unlinked | 1: `none_needed_already_terminated`, records `F\0` | `invalid_json` / `invalid_utf8`, n + 1 bytes, `has_repair_record` true |
| 3 .. r (part of R) | `F\0\n` + partial R | F invalid, partial R `incomplete_last_line` | 1: isolates the partial R line (line 4, marked) | F `invalid_json` / `invalid_utf8`, n + 1 bytes, `has_repair_record` false |
| r + 1 (all but R's final newline) | `F\0\n` + R without newline | F `isolated_by_repair` (linked through the unterminated R) | 1: marks R (`missing_trailing_newline`), R recoverable from the retry's `fragment_b64` | F `invalid_json` / `invalid_utf8`, `has_repair_record` false |
| r + 2 (complete) | `F\0\n` + R | F `isolated_by_repair` | 0 | `isolated_by_repair`, n + 1 bytes |

At every cut and after every retry: the original bytes are an unchanged prefix (sha256), only acknowledged Samples are counted, preceding records are read in order, and two further repairs return None and change nothing. Markers are never stripped. On retries the recorded fragment may include earlier markers, and the original fragment is always its prefix. A flush or fsync failure leaves the whole buffer on disk with no record returned; the next repair returns None (tail clean) and the line is `isolated_by_repair`. As before, that is not proof of durability (task 3.2).
