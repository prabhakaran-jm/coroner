# Requirements Document

## Introduction

Milestone M1 adds the Coroner Viewer: a read-only, localhost-only forensic investigation workstation over the saved M0 run artifacts. The Viewer answers one question for a dead container: "When this container died, what do we know, what evidence survived, and what remains uncertain?" Its headline message is "The same exit code does not always mean the same failure": Experiment_A (ExitCode 1), Experiment_B (ExitCode 137, OOMKilled false) and Experiment_C (ExitCode 137, OOMKilled true) are shown side by side, and the evidence survives all three deaths in the recorded runs.

The Viewer separates observed evidence (Docker Container_State, persisted evidence records, actual Sample measurements) from interpretation, and never invents a root cause, memory measurement, confidence score or missing Sample. The Viewer reads `manifest.json`, `evidence.jsonl` and `docker_inspect.json` from each run directory under `runs/`. The Viewer reads each artifact as bounded binary input (at most 16 MiB) and passes the bytes to the M0 functions `deserialize_manifest` (`coroner/runner/manifest.py`), `read_evidence` (`coroner/evidence/reader.py`, bytes form), `summarize` (`coroner/evidence/reader.py`) and `extract_inspect_excerpt` (`coroner/runner/manifest.py`). The Viewer validates run ids with `validate_run_id_for_path` (`coroner/runner/manifest.py`, which applies `RUN_ID_RE` from `coroner/evidence/schema.py`) and uses the public M0 functions `parse_utc_ms` and `format_utc_ms` (`coroner/common/timeutil.py`) for timestamps. The Viewer never uses the private M0 helper `_fmt`. The Viewer does not import `parse_docker_time` from `coroner/runner/experiments/base.py`, because importing that module loads `subprocess`, `urllib.request`, `coroner.runner.docker_port` and `coroner.runner.collector_client`; the Viewer instead keeps a local Docker_Time_Parser with the same behaviour, and a parity test (which imports the M0 function) pins the two together. M0 code is neither moved nor edited. The Viewer does not call the path-based M0 functions `read_manifest(Path)`, `read_evidence(Path)` or `build_summary(runs_dir, run_id)`, because they read whole files without a size bound. The Viewer changes no M0 behaviour, schema or artifact, does not run experiments and does not use Docker.

Requirement 12 maps every Viewer datum to its exact M0 source field. Requirement 15 defines how the four clocks in the artifacts are presented and which cross-clock comparisons are shown. Requirement 14 defines which Docker state source wins and how disagreements are shown. Requirement 16 defines the bounded artifact reads.

## Glossary

Terms defined in `.kiro/specs/coroner-m0/requirements.md` keep their M0 meaning: Sample, Capture_Time, Receive_Time, RSS, Run_Manifest, Run_Identifier, Container_State, Durability_Level, Process_Durable, Crash_Durable, Gap_Record, Missing_Sample_Count, Unreconciled_Drop_Count, Malformed_Line, Evidence_Reader, Evidence_Store, Sampling_Limitations, Diagnostic_Metrics, Experiment_A, Experiment_B, Experiment_C, Experiment_Runner, Collector, Probe, Demo_App, Destructive_Endpoints. "Runner" in this document means the Experiment_Runner. New and M1-specific terms:

- **Viewer**: The Python package `coroner.viewer` that serves the read-only Viewer_API and the Viewer_UI on the loopback address.
- **Viewer_API**: The HTTP endpoints `GET /api/runs` and `GET /api/runs/{run_id}` served by the Viewer, and no others.
- **Viewer_UI**: The HTML, CSS and JavaScript pages served by the Viewer, with no frontend build step.
- **UI_Routes**: The GET routes `/`, `/runs/{run_id}`, `/compare` (with the optional query parameters `a`, `b` and `c`) and `/static/{asset}` that serve the Viewer_UI.
- **Runs_Directory**: The directory passed to the Viewer with `--runs-dir`, default `runs`, whose subdirectories are Run_Directories.
- **Run_Directory**: A subdirectory of the Runs_Directory named by a valid Run_Identifier that contains a directory entry named `manifest.json`, and normally `evidence.jsonl` and `docker_inspect.json`. A directory without a `manifest.json` entry is not a Run_Directory and is not a run.
- **Artifact_Limit**: 16 MiB (16,777,216 bytes), the largest size of one artifact file that the Viewer reads.
- **Bounded_Read**: Reading an artifact as binary input from one open handle, at most Artifact_Limit plus 1 bytes, as defined in Requirement 16.
- **Docker_Time_Parser**: The Viewer's local function that parses Docker RFC3339 timestamp strings with up to nine fractional digits and returns no value (`None`) for the Docker zero date `0001-01-01T00:00:00Z`. The Docker_Time_Parser is behaviourally equivalent to the M0 function `parse_docker_time` of `coroner/runner/experiments/base.py`, and Requirement 11 criterion 31 defines the parity test.
- **Original_Timestamp**: A timestamp string exactly as stored in an artifact.
- **Display_Timestamp**: The `format_utc_ms` rendering (UTC, millisecond resolution) of an Original_Timestamp, returned by the Viewer_API in a `<field>_display` field.
- **Last_Persisted_Sample**: The last `sample` record in the file order of the Evidence_Store file as read from `evidence.jsonl`. The Last_Persisted_Sample is not necessarily the Sample with the latest Capture_Time.
- **Latest_Capture_Sample**: The Sample with the latest Capture_Time among all valid Samples (the earliest by file order among equal values).
- **Artifact_Status**: The per-artifact state reported by the Viewer, one of six values: `ok`, `missing`, `unreadable`, `invalid`, `too_large` or `not_read`. The value `not_read` means the Viewer deliberately did not open the artifact because the manifest of the run is unusable (Requirement 3 criterion 16); it carries the reason `manifest_unusable` and is distinct from `missing`, which means the artifact was looked for and was absent or failed the containment checks.
- **Run_Order**: The deterministic order of runs: `start_time` descending, with runs that have no valid `start_time` after all runs that have one, and ties (equal `start_time` values, or both `start_time` values missing) broken by `run_id` descending, compared as plain strings.
- **Runs_Directory_Label**: The text the Viewer and the Viewer_API use to name the Runs_Directory: the value given with `--runs-dir` when that value is a relative path, and only the final path component of the value when that value is an absolute path (Requirement 3 criterion 9).
- **Documented_Additive_Field**: A Viewer_API response field that Requirement 9 does not list by name but that the design document defines, such as `experiment_type`, list-envelope metadata (including truncation information), `x_ms`, `skipped_before`, `time_axis` and Docker comparison metadata. Every Documented_Additive_Field is on an explicit response allowlist (Requirement 9 criterion 14).
- **Compare_Slot**: One of the three positions `a`, `b`, `c` of the compare page, intended for Experiment_A, Experiment_B and Experiment_C respectively.
- **Stored_Outcome**: The `outcome` field of a Run_Manifest, one of `passed`, `failed` or `aborted`.
- **Verdict**: The Viewer label derived only from the Stored_Outcome: PASS for `passed`, FAIL for `failed`, and UNKNOWN for `aborted`, a missing or unreadable manifest, or any other value. The Viewer does not recompute the Runner verdict.
- **Incident**: One Run_Directory shown by the Viewer. An Incident has an experiment type of A, B or C taken from the manifest `experiment` field, compared case-insensitively.
- **Observed_Evidence**: Values read from stored artifacts without interpretation: Docker ExitCode, OOMKilled, status, memory limit, recorded timestamps, evidence record counts, and Sample measurements.
- **Interpretation**: Any statement about cause, meaning or likelihood that is not an Observed_Evidence value. The only Interpretation text the Viewer shows is the M0 `termination_description`, `cause_label`, Sampling_Limitations and `limitations` strings stored in the artifacts, labelled as recorded by the Runner.
- **Not_Recorded**: The display state for a value that is absent, null, of the wrong type or outside its valid range in the artifacts. The Viewer renders Not_Recorded as the text "not recorded" and never as 0, false or an empty value. The Viewer_API renders Not_Recorded as JSON `null`.
- **Plottable_Sample**: A valid Sample record whose `rss_bytes` is an integer greater than or equal to 0.
- **Evidence_Gap**: A known break in the Sample series, taken from the full parsed evidence: a Gap_Record with recorded `first_missing_seq` and `last_missing_seq`, or a `silence_timeout` Gap_Record.
- **Chart_Cap**: 5,000, the largest number of Samples in the chart payload of one Incident.
- **Partial_View**: The state of an RSS_Timeline in which the number of Plottable_Samples exceeds the Chart_Cap and the plotted Samples are a deterministic selection.
- **RSS_Timeline**: The SVG chart of Sample RSS against Capture_Time for one Incident.
- **Termination_Marker**: A mark on the RSS_Timeline axis. The only Termination_Marker the Viewer draws is the Experiment_B SIGKILL marker defined in Requirement 15 criterion 17. Every other recorded termination-related time is shown as labelled text below the chart.
- **Evidence_Panel**: The "Evidence vs Uncertainty" panel of the Incident detail page with a KNOWN section and an UNKNOWN OR LIMITED section.
- **Container_Clock**: The clock of the Demo_App container, which stamps the Probe Capture_Time (`sample.ts`).
- **Collector_Clock**: The clock of the Collector, which stamps the Receive_Time (`recv_time`) and the `server_time` that the Runner used to measure the clock offset.
- **Host_Clock**: The clock of the host that runs the Runner, which stamps `start_time`, `end_time`, `times.crash_request_time`, `times.sigkill_sent_time` and `container_state.inspect_time`.
- **Docker_Clock**: The clock of the Docker daemon, which stamps `State.FinishedAt` in `docker_inspect.json` and, after M0 truncation to milliseconds, the manifest `container_finished_at`. No artifact records the difference between the Docker_Clock and the Host_Clock, the Collector_Clock or the Container_Clock.
- **Clock_Offset**: The manifest `clock_offset_ms` value, measured by the Runner as Collector `server_time` minus the host midpoint time. M0 documents a positive value as the Collector clock being ahead of the host.
- **Clock_Uncertainty**: The manifest `clock_offset_uncertainty_ms` value recorded by the Runner for the Clock_Offset. The Clock_Uncertainty covers the Collector_Clock to Host_Clock measurement only, and does not bound any difference involving the Docker_Clock or the Container_Clock.
- **Timing_Tolerance**: The manifest `sample_timing.tolerance_ms` value. The M0 constant `CLOCK_TOLERANCE_MS` fixes the maximum at 250 ms, and M0 accepts only an integer from 0 to 250 inclusive. The Viewer never changes or clamps the recorded value. The Viewer holds its own constant `VIEWER_CLOCK_TOLERANCE_MAX_MS` of 250, documented as mirroring `CLOCK_TOLERANCE_MS`, and uses it only to validate the recorded value (Requirement 15 criterion 30).
- **Valid_Tolerance**: A recorded `sample_timing.tolerance_ms` that is a JSON integer (not a boolean, not a float, not a string) from 0 to `VIEWER_CLOCK_TOLERANCE_MAX_MS` inclusive.
- **Corrected_Capture_Time**: For Experiment_B only, the derived value Capture_Time minus Clock_Offset, the M0 correction convention of `classify_b_samples` (`ts - clock_offset_ms`). The Viewer derives no Corrected_Capture_Time for Experiment_A or Experiment_C. The value is labelled "derived, not independently proven" whenever it is compared with a time on another clock.
- **Derived_Interval**: A signed time difference that the Viewer computes, for Experiment_B only, between two recorded times, for example from the Corrected_Capture_Time of the Last_Persisted_Sample or of the Latest_Capture_Sample to `container_finished_at` or to the SIGKILL send time, or from `container_finished_at` to the SIGKILL send time. The Viewer computes no Derived_Interval for Experiment_A or Experiment_C (Requirement 15 criterion 29). Every Derived_Interval is labelled "derived", is shown with the clock labels and the clock-uncertainty statements of Requirement 15, and is never presented as proof of the order of two events.
- **Raw_Inspect**: The file `docker_inspect.json` of a Run_Directory.
- **Manifest_Derived_State**: The Docker state read from the manifest `container_state` block.
- **Discrepancy**: A compared field for which Manifest_Derived_State and Raw_Inspect hold different non-null values.
- **Protected_Volumes**: The Docker volumes `coroner_coroner_evidence`, `coroner-spike_coroner_spike_evidence`, `coroner-m07_coroner_evidence`, `coroner-t83-m05_coroner_evidence`, `coroner-t83_coroner_evidence` and `coroner-repro_coroner_evidence`.

## Requirements

### Requirement 1: Launch the Viewer locally

**User Story:** As an investigator, I want to start the Viewer with one command, so that I can open saved runs in my browser without Docker.

#### Acceptance Criteria

1. WHEN the command `python -m coroner.viewer --runs-dir runs --host 127.0.0.1 --port 8765` is run, THE Viewer SHALL serve the Viewer_UI and the Viewer_API on 127.0.0.1 port 8765.
2. WHERE `--runs-dir` is omitted, THE Viewer SHALL use `runs` as the Runs_Directory.
3. IF `--host` is given with any value other than 127.0.0.1, THEN THE Viewer SHALL exit with a non-zero status and an error message that states the Viewer binds only to 127.0.0.1.
4. IF the Runs_Directory does not exist or is not a directory, THEN THE Viewer SHALL exit with a non-zero status and an error message that names the path.
5. THE Viewer SHALL be implemented in the separate package `coroner.viewer`, using FastAPI, with no database, no authentication, no npm dependency and no frontend framework.
6. THE Viewer SHALL run without a Docker daemon, a Docker client library, the Collector, the Demo_App or the Experiment_Runner.
7. THE Viewer SHALL leave the import behaviour and public behaviour of the `coroner.collector`, `coroner.probe`, `coroner.demo_app` and `coroner.runner` packages unchanged.
8. IF `--port` is not an integer from 1 to 65535, THEN THE Viewer SHALL exit with a non-zero status and an error message that names the invalid value.
9. THE Viewer SHALL bind its listening socket to the literal address 127.0.0.1 only, and SHALL NOT resolve the name `localhost` for binding, so that the Viewer never listens on `::1` or on any other address.
10. THE Viewer SHALL accept requests whose Host header names the exact hostname `127.0.0.1` or `localhost`, with the port rule defined in Requirement 13 criterion 9, and the acceptance of a Host header that names `localhost` SHALL NOT change the bind address defined in criterion 9.
11. WHERE `--port` is 80, THE Viewer SHALL accept a Host header of `127.0.0.1` or `localhost` without a port, and SHALL bind only to 127.0.0.1 as defined in criterion 9 (Requirement 13 criterion 9 defines the port rule).

### Requirement 2: Read-only and safe data access

**User Story:** As an investigator, I want the Viewer to be unable to change or leak anything, so that the evidence stays trustworthy and my machine stays safe.

#### Acceptance Criteria

1. THE Viewer SHALL expose no endpoint that starts, stops, kills, builds or inspects a Docker container, runs an experiment, or calls the Demo_App `/crash` or `/leak` endpoints.
2. THE Viewer SHALL open every file under the Runs_Directory in read-only mode and SHALL NOT create, modify, rename or delete any file under the Runs_Directory.
3. WHEN a request names a `run_id`, THE Viewer SHALL validate the `run_id` with the existing `RUN_ID_RE` rule through `validate_run_id_for_path` before any file access.
4. IF the `run_id` in a request is invalid or contains a path separator, a drive prefix or a `..` segment, THEN THE Viewer SHALL respond with HTTP 400 and SHALL NOT access the file system for that request.
5. IF a valid `run_id` names no Run_Directory, THEN THE Viewer SHALL respond with HTTP 404.
6. IF the Run_Directory or an artifact file is a symbolic link, a junction or another reparse point, or its resolved path lies outside the resolved Runs_Directory, or the opened artifact is not a regular file inside the Run_Directory, THEN THE Viewer SHALL treat the artifact as missing and SHALL NOT read the target; Requirement 16 defines the checks.
7. THE Viewer SHALL read only the files named `manifest.json`, `evidence.jsonl` and `docker_inspect.json` inside a Run_Directory.
8. THE Viewer SHALL read every artifact with a Bounded_Read as defined in Requirement 16, and IF an artifact exceeds the Artifact_Limit, THEN THE Viewer SHALL set the Artifact_Status of that artifact to `too_large` and SHALL apply the consequences defined in Requirement 3 criterion 12.
9. THE Viewer SHALL return only the fields the Viewer_UI needs, on an explicit response allowlist (Requirement 9 criterion 14), and SHALL NOT return host file paths (including `raw_inspect_path`, `host_copy_path`, `container_path`, `docker_inspect_path` and the absolute form of the Runs_Directory, for which Requirement 3 criterion 9 defines the Runs_Directory_Label), raw evidence lines, base64 fragments or the raw Docker inspect document.
10. THE Viewer_UI SHALL insert every value that originates from an artifact into the page with `textContent` or an equivalent text-only API, and SHALL NOT use `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write` or `eval` with artifact content.
11. THE Viewer SHALL return the original value of every artifact string field that has no length cap, and WHERE the Viewer caps the length of a free-text field, THE Viewer SHALL truncate the value only together with explicit truncation metadata in the same response block (a `truncated` flag and the original length), and SHALL NOT truncate a value silently.
12. IF an unexpected error occurs while the Viewer serves a request, THEN THE Viewer SHALL respond as defined in Requirement 9 criterion 10, and SHALL NOT include a host path, a traceback or an exception message in the response.

### Requirement 3: Run discovery and artifact parsing

**User Story:** As an investigator, I want the Viewer to list every saved run found in the runs directory, so that I can choose an incident to inspect.

#### Acceptance Criteria

1. WHEN `GET /api/runs` is requested, THE Viewer SHALL return one entry for each immediate subdirectory of the Runs_Directory whose name is accepted by `validate_run_id_for_path` and that contains a directory entry named `manifest.json`, whatever the readability or validity of that entry (Requirement 3 criterion 13 defines the listing of an unusable manifest).
2. THE Viewer SHALL skip entries of the Runs_Directory that are not Run_Directories, including loose files and subdirectories without `manifest.json`, without reporting an error.
3. THE Viewer SHALL parse each manifest by passing the Bounded_Read bytes to the M0 function `deserialize_manifest`, SHALL obtain the evidence counts of a run by passing the Bounded_Read bytes to `read_evidence` and the result to `summarize`, and SHALL NOT call `read_manifest(Path)`, `read_evidence(Path)` or `build_summary` and SHALL NOT re-implement manifest parsing, evidence parsing, gap accounting or Sample counting; the only M0 parsing rule the Viewer re-implements is the Docker_Time_Parser, which Requirement 11 criterion 31 pins to the M0 function `parse_docker_time` by a parity test.
4. IF the `manifest.json` entry of a directory is unreadable, is not valid JSON, fails Run_Manifest validation, or is `too_large`, THEN THE Viewer SHALL list the run with Verdict UNKNOWN, an error state, the reason as text, and every other value Not_Recorded, and SHALL continue listing other runs.
5. IF the manifest `run_id` differs from the Run_Directory name, THEN THE Viewer SHALL list the run with Verdict UNKNOWN and a reason that states the mismatch.
6. IF `evidence.jsonl` is missing, unreadable or `too_large` for a run, THEN THE Viewer SHALL show every value derived from the evidence (Sample count, Missing_Sample_Count, Unreconciled_Drop_Count, Malformed_Line count, first, peak and last RSS, and the RSS_Timeline) as Not_Recorded, and SHALL still show the manifest values.
7. IF `evidence.jsonl` contains Malformed_Lines, THEN THE Viewer SHALL exclude those lines from every count and from the RSS_Timeline, and SHALL report the Malformed_Line count for the run.
8. IF `evidence.jsonl` contains no valid record and at least one Malformed_Line, THEN THE Viewer SHALL report a Sample count of 0 with the Malformed_Line count, and SHALL label the evidence as having no valid record.
9. WHEN the Runs_Directory contains no Run_Directory, THE Viewer_UI SHALL show an empty state that states no saved runs were found, names the Runs_Directory_Label, and states that the Viewer does not generate runs; the Runs_Directory_Label is the `--runs-dir` value as supplied when that value is relative, and only its final path component when that value is absolute, so that no response or page contains an absolute host path (Requirement 16 criterion 10).
10. THE Viewer SHALL NOT substitute synthetic, sample or placeholder data for any missing artifact or value.
11. THE Viewer SHALL order the run list in Run_Order: `start_time` descending, runs without a valid `start_time` after all runs with one, and ties (including equal and missing `start_time` values) broken by `run_id` descending, so that identical artifacts always produce an identical order.
12. IF the Artifact_Status of an artifact is `too_large`, THEN THE Viewer SHALL reject the whole artifact, SHALL NOT parse a prefix or any part of the artifact, SHALL show every value derived from that artifact as Not_Recorded, and SHALL show a labelled error that names the artifact, the observed size as defined in Requirement 16 criterion 6 and the Artifact_Limit.
13. IF a directory has a `manifest.json` entry whose Artifact_Status is `too_large`, `unreadable`, `invalid`, or `missing` because the entry failed the containment checks of Requirement 16 criteria 2 and 4 (for example a symbolic link, a reparse point or a non-regular file), THEN THE Viewer SHALL list the directory as an UNKNOWN run with the Artifact_Status as the reason; a directory that has no `manifest.json` entry is not a run and THE Viewer SHALL NOT list the directory.
14. IF an M0 function raises an exception while the Viewer parses an artifact, THEN THE Viewer SHALL report a stable reason category for the affected artifact and SHALL NOT return the exception message when the message contains a host path.
15. THE Viewer SHALL treat a size exactly equal to the Artifact_Limit as within the limit.
16. IF the manifest of a run is unusable (its Artifact_Status is `too_large`, `unreadable`, `invalid` or `missing` as defined in criterion 13, or the manifest `run_id` differs from the Run_Directory name), THEN THE Viewer SHALL NOT open `evidence.jsonl` or `docker_inspect.json` of that run, SHALL set the Artifact_Status of each of those two artifacts to `not_read` with the reason `manifest_unusable`, and SHALL NOT report `not_read` as `missing`.
17. WHEN the Viewer_UI shows an artifact with the Artifact_Status `not_read`, THE Viewer_UI SHALL render the text "not read (manifest unusable)" for that artifact, SHALL show every value derived from that artifact as Not_Recorded, and SHALL NOT add a Viewer warning that describes the artifact as absent.
18. IF an unexpected error occurs while the Viewer builds the list entry of one run, THEN THE Viewer SHALL report a stable `internal_error` reason for that run only, SHALL list every other run normally, and SHALL respond to `GET /api/runs` with HTTP 200.

### Requirement 4: Investigation overview

**User Story:** As an investigator, I want a single overview page with the three crash scenarios, so that I can see at a glance what each saved incident shows.

#### Acceptance Criteria

1. WHEN the root page `/` is requested, THE Viewer_UI SHALL show the Coroner brand, the heading "Container Crash Forensics" and the subtitle "What survived after the process died?".
2. THE Viewer_UI SHALL show three incident cards labelled A, B and C, one for each experiment type, on the overview page.
3. THE Viewer_UI SHALL populate each incident card from the most recent run of that experiment type, defined as the first run of that type in Run_Order (Requirement 3 criterion 11), and SHALL show the run id on the card.
4. THE Viewer_UI SHALL show on each incident card the Verdict (PASS, FAIL or UNKNOWN), Docker ExitCode, OOMKilled, the preserved Sample count, and a link to the Incident detail page.
5. WHERE the manifest records a `collector_survival` check, THE Viewer_UI SHALL show the Collector survival result on the incident card.
6. IF no run of an experiment type exists in the run list, THEN THE Viewer_UI SHALL show that card with the label "no saved run found" and all values Not_Recorded.
7. THE Viewer_UI SHALL list every other discovered run, including additional runs of A, B or C and runs whose `experiment` value is not A, B or C, in Run_Order in a run list with the run id, experiment type, Verdict and a link to the Incident detail page.
8. THE Viewer_UI SHALL use a dark graphite colour palette with amber, red and purple accents, and SHALL show the Verdict by text label in addition to colour.
9. THE Viewer_UI SHALL display the Experiment_A description as "controlled fatal process exit via os._exit(1)" and SHALL NOT describe Experiment_A as an exception.
10. THE Viewer_UI SHALL load all styles, scripts and fonts from the Viewer itself and SHALL make no request to an external host; the standard SVG namespace string `http://www.w3.org/2000/svg`, used only as the namespace argument of `createElementNS`, is an identifier and not a request, and is the only URL permitted in the static assets (Requirement 11 criterion 43).
11. WHERE the Docker state of a run shown on an incident card has a Discrepancy, THE Viewer_UI SHALL show the text marker "DISCREPANCY" on that card.

### Requirement 5: Incident detail

**User Story:** As an investigator, I want the full recorded state of one incident, so that I can inspect what Docker and the Runner observed.

#### Acceptance Criteria

1. WHEN an Incident detail page is requested for a run, THE Viewer_UI SHALL show the run id, experiment type, start time and end time, each with its clock label from Requirement 15.
2. THE Viewer_UI SHALL show the Runner verdict as the Verdict together with the Stored_Outcome, and the failure code and message when the manifest records a failure.
3. THE Viewer_UI SHALL show the observed termination state as the Docker status, ExitCode and OOMKilled values, each labelled with the state source defined in Requirement 14.
4. THE Viewer_UI SHALL show the memory limit in MiB together with the byte value, and SHALL show Not_Recorded when the value is absent.
5. WHERE the memory limit is recorded as 0 bytes, THE Viewer_UI SHALL show "0 bytes (no memory limit configured)" and SHALL NOT show the value as Not_Recorded.
6. THE Viewer_UI SHALL show the manifest `termination_description` labelled as recorded by the Runner, and SHALL show the manifest `termination.cause_label` when the manifest records one.
7. THE Viewer_UI SHALL show the Durability_Level using the M0 terms Crash_Durable for the stored value `crash` and Process_Durable for the stored value `process`, and SHALL show any other stored value as text.
8. THE Viewer_UI SHALL show the evidence record count from the manifest and the number of valid records the Evidence_Reader read, and SHALL flag a difference between the two numbers.
9. THE Viewer_UI SHALL show the preserved Sample count, the Missing_Sample_Count, the Unreconciled_Drop_Count with its uncertainty flag, and the Malformed_Line count, using the numbers returned by the M0 `summarize` function over the full parsed evidence.
10. WHERE a value is absent, null, of the wrong type or outside its valid range, THE Viewer_UI SHALL show Not_Recorded and SHALL NOT show 0, false, an empty string or an inferred value.
11. WHERE the `warnings` list of the M0 `RunSummary` returned by `summarize` is not empty, THE Viewer_UI SHALL list the warnings as text, and THE Viewer SHALL add its own warnings only for the manifest-versus-evidence record count difference (criterion 8) and for an Artifact_Status other than `ok`.
12. THE Viewer_UI SHALL show the Last_Persisted_Sample (its `seq`, Capture_Time and Receive_Time) and the Latest_Capture_Sample (its `seq` and Capture_Time) as two separately labelled facts, WHERE both exist, and SHALL show the Receive_Time returned by `summarize` as `last_sample_time` under its own label "last Receive_Time", and SHALL NOT present any of the three as another; the labels stay distinct even when two of them refer to the same Sample.
13. WHERE the Incident is Experiment_B and a Derived_Interval is shown for the Last_Persisted_Sample or for the Latest_Capture_Sample (for example the time from the Corrected_Capture_Time of that Sample to the recorded `container_finished_at`, or to the SIGKILL send time), THE Viewer_UI SHALL label the interval "derived", SHALL name the Sample it uses, SHALL show the clock label of each of the two times, and SHALL show beside it the clock-uncertainty statements of Requirement 15 criterion 27.

### Requirement 6: Memory timeline

**User Story:** As an investigator, I want the RSS history of the dying process, so that I can see what the Probe measured before the evidence stopped.

#### Acceptance Criteria

1. THE Viewer_UI SHALL draw the RSS_Timeline as an inline SVG chart generated by JavaScript served by the Viewer, with no charting library and no build step.
2. WHILE the number of Plottable_Samples of an Incident is at most the Chart_Cap, THE RSS_Timeline SHALL plot one point for each Plottable_Sample, with the x position given by the Sample Capture_Time as defined in Requirement 15 criteria 11, 12 and 13 and the y position given by `rss_bytes`.
3. WHILE the number of Plottable_Samples of an Incident exceeds the Chart_Cap, THE Viewer_API SHALL return a Partial_View selection of at most the Chart_Cap Samples that is a function of the ordered Plottable_Samples only, so that identical artifacts always produce an identical selection.
4. THE Partial_View selection SHALL contain the first and the last Plottable_Sample in Capture_Time order (equal Capture_Times ordered by `seq`), and the Plottable_Sample with the highest `rss_bytes` (the earliest in that order of equal highest values), and SHALL keep the selected Samples in Capture_Time order, with equal Capture_Times ordered by `seq`.
5. THE Partial_View selection SHALL contain only Samples that exist in the evidence, and THE RSS_Timeline SHALL NOT create, interpolate or smooth any point.
6. WHILE the RSS_Timeline is a Partial_View, THE Viewer_UI SHALL show next to the chart and next to the Sample table the label "Partial view" with the total number of valid Samples and the number of plotted Samples.

### Requirement 7: Evidence vs Uncertainty panel

**User Story:** As an investigator, I want known facts and unknowns separated, so that I do not mistake interpretation for evidence.

#### Acceptance Criteria

1. THE Evidence_Panel SHALL contain a section titled KNOWN and a section titled UNKNOWN OR LIMITED.
2. THE KNOWN section SHALL list the Docker-observed exit state (status, ExitCode, OOMKilled) with its state source label, the persisted evidence record count, the preserved Sample count, and the first, highest and last-persisted RSS values as defined in Requirement 12 criterion 8, each labelled with its definition and computed from the full parsed evidence.
3. THE UNKNOWN OR LIMITED section SHALL state that the interval between the last persisted Sample and the actual termination time is unobserved, using the M0 `UNOBSERVED_NOTE` text; WHERE a Derived_Interval is shown for that interval (Requirement 5 criterion 13), THE section SHALL label it "derived", and SHALL state that the interval does not establish the order of the Sample and the termination.
4. WHEN the Incident is Experiment_C, THE UNKNOWN OR LIMITED section SHALL state that growth after the Last_Persisted_Sample may be unsampled, and SHALL include the recorded Sampling_Limitations statements.
5. WHERE the Unreconciled_Drop_Count is greater than 0 or Malformed_Lines exist, THE UNKNOWN OR LIMITED section SHALL list the unreconciled drops with their uncertainty and the Malformed_Line count.
6. THE UNKNOWN OR LIMITED section SHALL state that a root cause is not established by the recorded evidence, and SHALL NOT assert a diagnosis, a confidence score or a probability.
7. THE Evidence_Panel SHALL show any text that originates from the Runner (termination_description, cause_label, limitations) labelled "recorded by the Runner" and visually separate from the KNOWN section.
8. WHERE a value needed for an entry is Not_Recorded, THE Evidence_Panel SHALL list the entry under UNKNOWN OR LIMITED as "not recorded".
9. THE Evidence_Panel SHALL show each entry with a text label of KNOWN or UNKNOWN OR LIMITED, in addition to colour.
10. WHERE a Discrepancy exists for a Docker state field, THE Evidence_Panel SHALL list the Discrepancy under UNKNOWN OR LIMITED with the field name and both values.
11. WHEN the Incident is Experiment_A or Experiment_C, or Requirement 15 states that clock correction is unavailable, THE Evidence_Panel SHALL list under UNKNOWN OR LIMITED that the ordering of Capture_Time against Host_Clock and Docker_Clock times is not established, and for Experiment_A and Experiment_C SHALL list the raw Capture_Time and the Docker `FinishedAt` as separate recorded values with no interval between them.
12. WHEN the Incident is Experiment_B, THE Evidence_Panel SHALL list under UNKNOWN OR LIMITED that every comparison of a Corrected_Capture_Time or of the Docker `FinishedAt` with the SIGKILL send time is "derived, not independently proven", and that the recorded Clock_Uncertainty does not bound the Docker_Clock.
13. THE Evidence_Panel SHALL NOT state or imply that the recorded Collector_Clock to Host_Clock uncertainty proves that the Container_Clock and the Docker_Clock are equivalent.

### Requirement 8: Compare incidents

**User Story:** As an investigator, I want to compare A, B and C, so that I can see that the same exit code does not always mean the same failure.

#### Acceptance Criteria

1. WHEN the compare page `/compare` is requested, THE Viewer_UI SHALL show Experiment_A, Experiment_B and Experiment_C side by side with run id, Verdict, ExitCode, OOMKilled, memory limit, preserved Sample count and highest Sample RSS.
2. THE Viewer_UI SHALL compute each comparison statement from the stored ExitCode and OOMKilled values of the compared runs and SHALL NOT use fixed text for a comparison result.
3. WHEN the ExitCode of Experiment_A differs from the ExitCode of Experiment_B and of Experiment_C, THE Viewer_UI SHALL state that Experiment_A differs from Experiment_B and Experiment_C by exit code, and SHALL show the three ExitCode values.
4. WHEN Experiment_B and Experiment_C both have ExitCode 137, THE Viewer_UI SHALL state that Experiment_B and Experiment_C share ExitCode 137.
5. WHEN Experiment_B and Experiment_C both have ExitCode 137 and differ in OOMKilled, THE Viewer_UI SHALL state that OOMKilled distinguishes Experiment_B (false) from Experiment_C (true).
6. WHEN every compared run has at least one preserved Sample, THE Viewer_UI SHALL state that evidence survived all three deaths in the recorded runs.
7. IF a compared experiment type has no saved run, an unavailable or excluded Compare_Slot (criteria 11 and 12) or a missing value, THEN THE Viewer_UI SHALL omit every comparison statement that depends on the missing value and SHALL state which run or value is missing.
8. THE Viewer_UI SHALL show the message "The same exit code does not always mean the same failure" on the compare page only WHEN Experiment_B and Experiment_C are both present, both have ExitCode 137, and have different OOMKilled values.
9. THE Viewer_UI SHALL let the user choose which saved run of each experiment type is compared, defaulting, for each Compare_Slot whose query parameter is absent, to the first run of the slot's experiment type in Run_Order (Requirement 3 criterion 11), so that the default is deterministic for identical artifacts.
10. WHEN `GET /compare` is requested with the query parameters `a`, `b` or `c`, THE Viewer SHALL validate each supplied value with `validate_run_id_for_path` before any file access, and IF any supplied value is invalid, THEN THE Viewer SHALL respond with HTTP 400 for the whole request and SHALL NOT access the file system; IF the request has a query parameter other than `a`, `b` or `c`, or has any of `a`, `b` or `c` more than once, or has an empty value for one of them, THEN THE Viewer SHALL respond with HTTP 400 for the whole request and SHALL NOT access the file system.
11. IF a supplied `a`, `b` or `c` value is a valid run id that names no Run_Directory, THEN THE Viewer_UI SHALL answer the `/compare` request with HTTP 200 and SHALL show that Compare_Slot in an "unavailable" state that names the run id and states that no saved run was found, instead of an error page, and SHALL omit that slot from every comparison statement.
12. IF the run supplied for a Compare_Slot has an experiment type different from the type of the slot (for example an Experiment_B run supplied as `a`), THEN THE Viewer_UI SHALL show a visible warning that names the run id, its experiment type and the expected type, SHALL still show the run's values labelled with its actual type, and SHALL exclude the run from every comparison statement, including the statements of criteria 3 to 6 and the message of criterion 8.
13. IF a compared run has a Discrepancy in ExitCode or OOMKilled, THEN THE Viewer_UI SHALL omit every comparison statement that depends on the discrepant field and SHALL state that the Docker state sources disagree.
14. THE `/compare` page SHALL obtain run data only from `GET /api/runs` and `GET /api/runs/{run_id}`, SHALL add no API route, and SHALL treat an HTTP 404 from `GET /api/runs/{run_id}` as the "unavailable" state of criterion 11.
15. THE Viewer_UI SHALL compute the comparison statements of criteria 2 to 8 and 13 in browser-side JavaScript served by the Viewer, from the stored values of the two API routes, and THE Viewer SHALL verify that logic as defined in Requirement 11 criteria 32 to 34.

### Requirement 9: Viewer API contract

**User Story:** As a frontend developer, I want a small stable API, so that the Viewer_UI gets exactly the fields it renders.

#### Acceptance Criteria

1. WHEN `GET /api/runs` is requested, THE Viewer_API SHALL return a JSON object with a `runs` list in which each entry has at least `run_id`, `experiment`, `verdict`, `start_time`, `start_time_display`, `exit_code`, `oom_killed`, `sample_count`, `collector_survival`, `docker_state_source`, `docker_state_discrepancy` and `reason`, plus the Documented_Additive_Fields defined in the design (including `experiment_type` and the listing metadata such as the Runs_Directory_Label and truncation information), and the list SHALL be in Run_Order.
2. WHEN `GET /api/runs/{run_id}` is requested for an existing run, THE Viewer_API SHALL return a JSON object with exactly the blocks `run`, `docker_state`, `timing`, `termination_markers`, `evidence_summary`, `chart`, `runner_text`, `artifact_status` and `warnings`.
3. THE `chart` block SHALL contain at least `total_samples` (the count of valid Sample records in the full parsed evidence), `plottable_samples`, `unplottable_samples`, `plotted_samples` (the length of `points`), `partial_view` (a boolean), `chart_cap` (5000), `points` and `gaps`, plus the Documented_Additive_Fields (including `time_axis`).
4. THE `chart.points` list SHALL hold at most the Chart_Cap entries in Capture_Time order, each with at least `seq`, `capture_time`, `capture_time_display`, `receive_time`, `receive_time_display`, `corrected_capture_time` (Experiment_B with a recorded Clock_Offset only, otherwise `null`), `rss_bytes` and `gap_before`, plus the Documented_Additive_Fields (including `x_ms`, the x position that the Viewer computes so that the Viewer_UI parses no timestamp, and `skipped_before`, the number of Samples with no RSS between the entry and the previous entry), where `gap_before` is true when an Evidence_Gap lies between the entry and the previous entry.
5. THE `chart.partial_view` field SHALL be true if and only if `plottable_samples` is greater than `chart_cap` for that invocation (Requirement 6 criterion 22).
6. THE `evidence_summary` block SHALL hold the full-run statistics defined in Requirement 6 criterion 7, and the values SHALL be identical whether or not `chart.partial_view` is true.
7. THE Viewer_API SHALL return JSON `null` for every value that is not recorded, and SHALL NOT substitute 0, false or an empty string.
8. THE Viewer_API SHALL return JSON with no NaN or Infinity values.
9. THE `artifact_status` block SHALL hold the Artifact_Status (one of the six values `ok`, `missing`, `unreadable`, `invalid`, `too_large`, `not_read`) of `manifest.json`, `evidence.jsonl` and `docker_inspect.json`, a stable `reason` string for every status other than `ok` (the reason is `manifest_unusable` for `not_read`), and the observed size (as defined in Requirement 16 criterion 6) and the Artifact_Limit when the status is `too_large`.
10. IF an unexpected error occurs while the Viewer serves `GET /api/runs/{run_id}`, THEN THE Viewer_API SHALL respond with HTTP 500 and a JSON error object that has a stable error code and no stack trace, exception message or host path, and SHALL continue serving other requests; IF the unexpected error occurs for one run while the Viewer serves `GET /api/runs`, THEN THE Viewer_API SHALL affect only the entry of that run (Requirement 3 criterion 18).
11. THE `evidence_summary` block SHALL return the Last_Persisted_Sample (`seq`, `capture_time`, `receive_time` and their `_display` fields) and the Latest_Capture_Sample (`seq`, `capture_time` and its `_display` field) as separate objects, and the `summarize` value `last_sample_time` as a separate field named `last_receive_time_summary`, each `null` when not recorded.
12. THE Viewer_API SHALL return the timestamp fields as defined in Requirement 15 criterion 3: the Original_Timestamp unchanged in the recorded field and the Display_Timestamp in the sibling `_display` field, and the Viewer_UI SHALL perform no timestamp parsing or rounding of its own.
13. THE `timing` block SHALL return the Original_Timestamp and Display_Timestamp of `start_time`, `end_time`, `inspect_time`, `times.crash_request_time`, `times.sigkill_sent_time`, `container_finished_at` and the raw `State.FinishedAt`, the Clock_Offset, the Clock_Uncertainty and the Timing_Tolerance, each with a `clock` string naming its clock, and SHALL return no host-equivalent value and no Derived_Interval for Experiment_A or Experiment_C; the Timing_Tolerance is returned as recorded together with its validity status (Requirement 15 criterion 30).
14. THE Viewer_API SHALL build every response object from an explicit allowlist of field names for that object, and the allowlist SHALL contain the fields that criteria 1 to 13 require plus the Documented_Additive_Fields that the design defines; a field that is on no allowlist SHALL NOT appear in a response, and the fields required by criteria 1 to 13 SHALL remain present in every response of the matching route.
15. THE Viewer_API SHALL return the Runs_Directory only as the Runs_Directory_Label, and SHALL return an artifact free-text field in full unless the field has a documented cap, in which case the Viewer SHALL return the truncated value together with a `truncated` flag and the original length (Requirement 2 criterion 11).

### Requirement 13: Route surface and request guard

**User Story:** As an investigator, I want the Viewer to expose only the routes it needs and to defend against hostile web pages, so that a browser tab on my machine cannot read or change my evidence.

#### Acceptance Criteria

1. THE Viewer SHALL serve the UI_Routes `GET /` (overview page), `GET /runs/{run_id}` (Incident detail page), `GET /compare` (compare page, with the optional query parameters `a`, `b` and `c`, each at most once, and no other query parameter, as Requirement 8 criterion 10 defines) and `GET /static/{asset}` (static assets), and SHALL register no other UI route.
2. THE Viewer SHALL serve exactly two API routes, `GET /api/runs` and `GET /api/runs/{run_id}`, and SHALL register no other path under `/api`.
3. WHEN a request names a path that is not registered, THE Viewer SHALL respond with HTTP 404.
4. THE Viewer SHALL create the FastAPI application with the interactive documentation and schema endpoints disabled, so that `/docs`, `/redoc` and `/openapi.json` respond with HTTP 404.
5. IF a request uses an HTTP method other than GET, including HEAD, OPTIONS, POST, PUT, PATCH and DELETE, THEN THE Viewer SHALL respond with HTTP 405 and an `Allow: GET` header, and SHALL change no file.
6. THE Viewer SHALL serve `GET /static/{asset}` only from a fixed directory inside the `coroner.viewer` package, and SHALL respond with HTTP 404 for any asset name that is not a file directly in that directory, including names with a path separator, a `..` segment or a drive prefix.
7. THE Viewer SHALL serve no file from the Runs_Directory through `/static/`.
8. THE Viewer SHALL validate the `run_id` of `GET /runs/{run_id}` and of `GET /api/runs/{run_id}` with `validate_run_id_for_path`, and SHALL respond with HTTP 400 for an invalid value and HTTP 404 for a valid value that names no Run_Directory.

WHEN a request arrives, THE Viewer SHALL accept the Host header only if the hostname is exactly `127.0.0.1` or exactly `localhost` (compared case-sensitively and byte for byte) and the port part equals `<port>`, the port the Viewer serves, or, WHERE `<port>` is 80, the Host header has no port part; THE Viewer SHALL respond with HTTP 421 for any other Host header value, including `[::1]:<port>`, a Host header without a port WHEN `<port>` is not 80, a different hostname, a hostname with a trailing character, and a Host header with a different port.
10. IF a request has no Host header or more than one Host header, THEN THE Viewer SHALL respond with HTTP 400.
11. THE Viewer SHALL set the response header `Content-Type: application/json` and the response header `X-Content-Type-Options: nosniff` on API responses.
12. THE Viewer SHALL set the response header `Cache-Control: no-store` on every API response and every UI_Routes response.
13. THE Viewer SHALL add no `Access-Control-Allow-Origin` header or other CORS header to any response and SHALL install no CORS middleware.
14. THE Viewer SHALL set a `Content-Security-Policy` response header on every HTML response that restricts scripts, styles, images, fonts and connections to the Viewer's own origin and forbids framing of the page.
15. THE Viewer SHALL use `RUN_ID_RE` through `validate_run_id_for_path` as the only rule that decides whether a run id is valid, without a second pattern.
16. WHEN `GET /compare` is requested, THE Viewer SHALL apply the validation and the HTTP 400 response defined in Requirement 8 criterion 10 (including the HTTP 400 for an unknown or repeated query parameter), and SHALL answer a valid but nonexistent run id with HTTP 200 and the "unavailable" slot state defined in Requirement 8 criterion 11.
17. THE Viewer SHALL bind exclusively to the literal address 127.0.0.1 as defined in Requirement 1 criterion 9, independently of the Host header values accepted in criterion 9.

### Requirement 14: Docker state sources and discrepancies

**User Story:** As an investigator, I want to know whether the Docker state shown comes from the raw inspect file or only from the manifest, and to see any disagreement, so that I never rely on a silently chosen value.

#### Acceptance Criteria

1. THE Viewer SHALL read the Raw_Inspect by a Bounded_Read, and SHALL pass the bytes to `extract_inspect_excerpt` for the container id, status, ExitCode, OOMKilled and memory limit, and to the Docker_Time_Parser for `State.FinishedAt` (a Docker zero date or an unparseable value is Not_Recorded for comparison and display).

9. WHILE a Discrepancy exists, THE Viewer_UI SHALL keep showing the Verdict derived from the Stored_Outcome of the manifest.
10. THE Viewer_API SHALL return in the `docker_state` block a `source` string, the manifest values, the raw inspect values (or `null`) and a `discrepancies` list of objects with `field`, `manifest_value` and `raw_value`.

WHEN the Viewer_UI shows a derived Experiment_B interval between the Corrected_Capture_Time and the SIGKILL send time, THE Viewer_UI SHALL show the Clock_Uncertainty and the Timing_Tolerance with the interval; IF the Clock_Uncertainty is Not_Recorded, THEN THE Viewer_UI SHALL show no interval and no ordering; IF the Timing_Tolerance is not a Valid_Tolerance (criterion 30), THEN THE Viewer_UI SHALL show the interval without any ordering statement.

WHEN the Viewer_UI shows the interval between the Docker `FinishedAt` and the SIGKILL send time, THE Viewer_UI SHALL show the signed difference labelled "derived, not independently proven" with the statement that no recorded bound exists for the Docker_Clock, and SHALL NOT state which time came first.

THE Viewer_UI SHALL show the recorded `sample_timing` values (`pre_kill_count`, `pre_kill_late_received_count`, `within_tolerance_count`, the count and the Capture_Time strings of `post_kill_beyond_tolerance`, the count and the Capture_Time strings of `after_container_stop`, and `tolerance_ms`) for Experiment_B exactly as the Runner stored them, and SHALL NOT recompute any classification.

24. WHERE `sample_timing.after_container_stop_analysis` is `unavailable`, THE Viewer_UI SHALL state that the analysis relative to the container stop is unavailable and SHALL NOT show an `after_container_stop` count of 0.
25. THE Viewer_UI SHALL present the Docker_Clock `FinishedAt` as recorded by the Docker daemon, with no correction applied by M0 and none applied by the Viewer.
26. WHERE the clock offsets conflict (criterion 7), THE Viewer SHALL suppress every derived marker and every Derived_Interval that depends on a Clock_Offset, and THE Viewer_UI SHALL state that the derived values are suppressed because the recorded clock offsets disagree.

WHERE the Viewer shows a Derived_Interval for the Last_Persisted_Sample or the Latest_Capture_Sample (Requirement 5 criterion 13), THE Viewer_UI SHALL label the interval "derived", SHALL label each of the two times with its clock, SHALL state that the four clocks (Container_Clock, Collector_Clock, Host_Clock and Docker_Clock) are not recorded as synchronised, SHALL state that the Clock_Uncertainty does not bound the Docker_Clock or the Container_Clock, SHALL apply criteria 19, 20 and 21 to the interval where they apply, and SHALL NOT state or imply that the interval proves the order of two events; this criterion applies to Experiment_B only, because criterion 29 forbids a Derived_Interval for Experiment_A and Experiment_C.

THE Viewer SHALL treat a recorded `sample_timing.tolerance_ms` as a Valid_Tolerance only when the value is a JSON integer (a boolean is excluded) from 0 to 250 inclusive, using the Viewer's own constant `VIEWER_CLOCK_TOLERANCE_MAX_MS` of 250 that mirrors the M0 constant `CLOCK_TOLERANCE_MS` without importing it; IF `tolerance_ms` is missing, is not an integer, is a boolean, or lies outside 0 to 250, THEN THE Viewer SHALL make the derived ordering unavailable for that run (no `ordering` value on any Derived_Interval, with a stable reason code), SHALL NOT clamp or replace the value, and SHALL return and show the recorded value unchanged with the note "out of range" or "not recorded" as applicable.

### Requirement 16: Bounded artifact reads and path containment

**User Story:** As an investigator, I want every artifact read to be bounded and contained, so that a huge, growing or redirected file cannot exhaust memory or leak data from outside the runs directory.

#### Acceptance Criteria

1. THE Viewer SHALL resolve the Runs_Directory once at start-up and SHALL build every artifact path from the resolved Runs_Directory, a run id accepted by `validate_run_id_for_path`, and one of the three fixed artifact names.
2. IF the Run_Directory or an artifact entry is a symbolic link, a junction or another reparse point, or is not the expected kind (a directory for the Run_Directory, a regular file for an artifact), THEN THE Viewer SHALL set the Artifact_Status to `missing` for the artifact, SHALL NOT open the target, and SHALL NOT read it.
3. THE Viewer SHALL open each artifact in read-only binary mode with no-follow semantics where the platform provides them (`O_NOFOLLOW` on POSIX), and on a platform without no-follow semantics SHALL check the link and reparse-point state of the entry immediately before opening.
4. AFTER opening an artifact, THE Viewer SHALL verify from the open handle that the opened file is a regular file and that its identity (device and file index where the platform provides them) equals the identity of the checked entry, and SHALL verify that the resolved path of the entry lies inside the resolved Run_Directory; IF a check fails, THEN THE Viewer SHALL set the Artifact_Status to `missing` and SHALL close the handle without reading.
5. THE Viewer SHALL read the artifact from the open handle in chunks and SHALL read at most Artifact_Limit plus 1 bytes in total, whatever the size reported by `stat` before or after opening, so that a file that grows between a size check and the read cannot exceed the bound.
6. IF the Bounded_Read yields more than the Artifact_Limit bytes, THEN THE Viewer SHALL set the Artifact_Status to `too_large`, SHALL discard the bytes read, SHALL parse nothing from the artifact, SHALL return every value derived from the artifact as `null`, and SHALL report the observed size as "more than 16,777,216 bytes" together with the Artifact_Limit.
7. WHEN the Bounded_Read yields at most the Artifact_Limit bytes, THE Viewer SHALL pass the bytes (and no path) to `deserialize_manifest` for `manifest.json`, to `read_evidence` for `evidence.jsonl` and to `extract_inspect_excerpt` and the Docker_Time_Parser for `docker_inspect.json`, and SHALL pass the `ReadResult` to `summarize`.
8. THE Viewer MAY perform a preliminary `stat` size check as an early rejection, and the check SHALL NOT replace the Bounded_Read.
9. IF opening or reading an artifact raises an operating-system error other than a missing file, THEN THE Viewer SHALL set the Artifact_Status to `unreadable` and SHALL return a stable reason category without the host path or the operating-system message.
10. THE Viewer SHALL NOT include an absolute host path in any API response, HTML page, log line shown to the user or error message, and SHALL show a run only by its run id; WHERE `--runs-dir` is an absolute path, THE Viewer SHALL show the Runs_Directory only as its final path component, and WHERE `--runs-dir` is relative, THE Viewer MAY show it as supplied (Requirement 3 criterion 9).
11. THE Viewer MAY cache parsed results keyed by a stat signature of the artifacts (size, modification time and file identity); the cache SHALL be a local, single-user convenience, and THE Viewer documentation SHALL state the limitation that an artifact rewritten with the same size, modification time and file identity (deliberate metadata forgery) can be served from the cache, and no requirement or document SHALL claim that the cache can never be stale.
